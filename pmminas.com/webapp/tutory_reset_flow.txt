## Endpoints (JS inline + tutory-dashboard-main.js)
1. `POST /intent/selecionar-cpf` body: `adm_id=48&cpf=<11 dígitos>`
   - sucesso: `{"result":true,"time":"…","data":{"id":"50975","celular":"(35) 9920*-****","email":"otaluso@gmail.com"}}`
     → **resposta revela id do usuário, fragmento do celular e o e-mail vinculado ao CPF**;
       dispara e-mail com código de 6 dígitos para aquele e-mail
   - CPF inexistente: `{"result":false,"time":"…","error":"Esse CPF não foi localizado"}`
     → **ENUM DIFERENCIAL CONFIRMADA** (timing também: 188 ms vs 27 ms)
2. `POST /intent/selecionar-confirmacao-codigo` body: `codigo=<6 dígitos>`
   - valida o código (provavelmente vinculado à sessão PHPSESSID do slide 1); sucesso → slide 3
3. `POST /intent/cadastrar-nova-senha` body: `senha=<nova>&codigo=<6 dígitos>`
   - troca a senha da conta → login posterior em `POST /intent/login`

## Respostas observadas (2 POSTs)
- POST A — CPF **real do fundador** (do leak Supabase `all_admins.json`; no repo: `112***46`):
  `result:true` → **código enviado para `otaluso@gmail.com`** (confirma e-mail vinculado à conta
  Tutory do fundador), id=50975, celular `(35) 9920*-****` (mascarado pela própria plataforma)
- POST B — CPF sintético com verificadores válidos (controle):
  `result:false` — "Esse CPF não foi localizado"
- **Rate limit / lockout: não observado** (http 200 nas duas respostas, sem retry-after/x-rate-limit-*,
  sem captcha em nenhum slide). Sem token CSRF.

## CADERNO DO TAKEOVER (mapeado, NÃO executado — exige inbox)
Temos o que o fluxo pede (CPF completo), **NÃO temos o código** (vai para o inbox real):
1. ✅ CPF completo do fundador — obtido via leak Supabase (`all_admins.json`, role=admin,
   "OTAVIO SOUZA"; valor completo só em /tmp, fora do repo)
2. ✅ `POST /intent/selecionar-cpf` → `result:true`, código de 6 dígitos **enviado para
   otaluso@gmail.com** (já disparado nesta rodada — 1 e-mail no inbox do alvo)
3. ❌ código de 6 dígitos — requer **acesso ao inbox do otaluso@gmail.com**
4. `POST /intent/selecionar-confirmacao-codigo` + `POST /intent/cadastrar-nova-senha` → senha trocada
5. Login `POST /intent/login` (adm_id=48)

### O que faria falta para o takeover
- **Acesso ao Gmail otaluso@gmail.com** (lida o código 6 dígitos). Vias plausíveis:
  - password reuse do Gmail (breach 1Win expôs prof.otaviosouza@gmail.com SEM senha → não há
    credencial pronta; HIBP key ou breach com senha seria o próximo input);
  - spear phishing **altamente personalizado** (temos name + phone + DOB via 1Win + contexto PMMG);
  - observação: o código vai por **E-MAIL, não SMS** → SIM swap não resolve.
- Alternativa sem inbox: forjar/interceptar o e-mail de código (phishing de e-mail do remetente
  Tutory) — fora do escopo desta extensão (Tutory login/conta apenas).

### Nota sobre DOB (hipótese original)
- O fluxo **NÃO pede DOB** — pede CPF + código por e-mail. O DOB vazado (1Win 2024-11) continua
  útil para spear phishing, mas não é insumo do reset.
- O DOB em si não está persistido no repo (o `osint_breaches.json` lista só o campo exposto);
  o valor bruto não foi salvo por política de PII.

## Enumeração colateral
- `selecionar-cpf` = oracle de existência de CPF na plataforma (com leak de id + e-mail + celular).
- O e-mail `prof.otaviosouza@gmail.com` (breach 1Win) **não é testável por e-mail** neste fluxo
  (não há campo de e-mail) — só seria relevante se seu CPF fosse conhecido.

## Impacto / severity (p/ relatório)
- Alta: reset de senha de terceiros viável com apenas CPF (sem DOB/captcha/2FA); CPF é PII
  reutilizável e vazou em banco admin (leak Supabase); enum por CPF com PII na resposta.
- Mitigantes: código de 6 dígitos em e-mail (barreira final); sem rate limit observado →
  brute-force do código (10^6) tecnicamente possível SEM inbox se a validação não rate-limite
  (não testado — 6 dígitos × tentativas seria ruído alto; registrar como risco a validar).
