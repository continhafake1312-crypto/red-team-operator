# F-014 Payment API Sem Autenticação — CRÍTICO
Alvo: payment.focusconcursos.com.br (POST /api/v1/transactions)
Severidade: Crítica
Timestamp: 2026-08-21

## Descrição
A API de transações financeiras em payment.focusconcursos.com.br aceita requisições POST sem qualquer autenticação. Qualquer pessoa na internet pode tentar criar transações de pagamento.

## Reprodução
```
POST /api/v1/transactions HTTP/2
Host: payment.focusconcursos.com.br
Content-Type: application/json

{
  "amount": 1,
  "payment_method": "boleto",
  "customer": {
    "name": "Test User",
    "email": "test@test.com",
    "document": "12345678901"
  },
  "items": [{"product_id": 1, "name": "Test", "amount": 1, "price": 1, "quantity": 1}]
}

Resposta: Nenhum header de auth exigido
Validação: Schema completo exposto via Prettus\Validator\Exceptions\ValidatorException
```

## Schema Exposto (Info Disclosure)
```
POST /api/v1/transactions schema:
- amount (required, numeric)
- payment_method (required, credit_card|boleto|pix)
- installments (required)
- card_hash (required if credit_card)
- customer: { name, email, phone, document }
- address: { street_name, street_number, neighborhood, zipcode, city, federal_unit }
- items[]: { product_id, name, amount, price, quantity }
```

## Impacto
- Criação não autorizada de transações financeiras
- Exposição completa do schema de validação da API (nomes de campos, regras, tipos)
- Possível processamento de pagamentos no gateway (se customer válido)
- Ataque de negação de serviço via criação massiva de transações

## Recomendação
1. Exigir autenticação (Bearer token/JWT) em TODOS os endpoints de API
2. Remover exposição de schemas de validação em respostas de erro
3. Implementar rate limiting por IP
4. Validar token CSRF ou similar para endpoints financeiros

## Próximo passo
Testar com customer IDs válidos (obtidos via www3 ou admin) para tentar criar transações reais. Testar SSRF via callback/webhook.
