## Etapa 2 — Confirmação do admin real no DB (R1, read-only)
```
SELECT p.id,p.email,p.name,r.name FROM person_role pr JOIN people p
  ON p.id=pr.persons_id JOIN roles r ON r.id=pr.roles_id
  WHERE r.name ILIKE '%admin%';
```
→ `admin@localhost.com` (id 00000000-0000-0000-0000-000000000001)
  possui role "Admin" (role_id=1). Existe também role "AdminSystem"(0).
  (10 admins enumerados no DB — não reproduzidos por PII.)

## Impacto (CRÍTICO)
- Qualquer atacante com o secret (vazado no GitLab CI em texto claro)
  pode forjar tokens admin e:
  - Enumerar TODOS os usuários (nome, email, CPF/documento, roles)
  - Acessar pedidos/pagamentos (PII + financeiro)
  - Operar como admin da plataforma (dependendo das rotas admin)
- Combina com R1 (DB direto) e VULN-04 (secrets em texto claro).
- `/debug/environment-variables` bloqueado = melhoria parcial, mas o
  núcleo da vuln (forge de token) permanece totalmente explorável.

## Recomendação
- Rotacionar IMEDIATAMENTE PROD_JWT_SECRET (e reemitir todos os tokens).
- Migrar o secret para um secret manager (AWS/Azure Vault), NÃO em CI
  variable em texto claro.
- Validar issuer/audience + exigir claims de autorização reais (RBAC
  server-side) — não confiar apenas na assinatura.
- Considerar RS256 (chave assimétrica) com rotação de chaves (JWKS).
- Bloquear/debug já feito; estender bloqueio de paths sensíveis no edge.

## OPSEC
- Apenas GET read-only (/orders, /users, /health, /debug/*).
- Nenhuma escrita/modificação. Tokens forjados usados apenas para probe.
- PII nos outputs: redigido nesta evidência (nomes/CPFs truncados).
- Conexão via Tor/proxychains4, bypass de Cloudflare via edge Caddy
  (--resolve api.dsoconcursos.com.br:443:201.54.0.48) — o vhost `api`
  passa pelo Caddy (diferente do `gitlab`, que é CF-only).
