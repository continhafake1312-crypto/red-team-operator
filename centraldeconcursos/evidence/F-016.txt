1. Enumeração de contas via oracle diferenciado (F-007 Seducar, F-012 CRM).
   OWA não tem oracle (reason=2 genérico para email existente/inexistente).
2. Cred-stuffing dirigido nos emails EXISTENTES (Seducar) com senhas BR/leak
   + padrões corporativos (Central@2025, Seducar@123, Igor@2025, etc.).
3. Threshold respeitado: max 5 por email Seducar (rate-limit 30min), max 3
   por email OWA (lockout AD), NEWNYM (rotação IP) entre emails.
4. OPSEC: Tor socks5 em todos os requests, UA rotativo, delay 8-14s.
5. Log de TODAS as tentativas em loot/cred_attempts.txt (timestamp ISO8601,
   email, senha, endpoint, código resposta, IP Tor).

## Limitações
- **Sem breach data:** HIBP/DeHashed/IntelX não acessíveis (sem API key —
  limitação herdada do recon). Cred-stuffing dirigido com senhas BR/leak
  genéricas tem baixa probabilidade contra senhas corporativas fortes. A
  aquisição de breach data dos 3 emails existentes (consultoriarepublica@,
  suporteead@, igor.velazquez@) aumentaria drasticamente a chance de sucesso.
- **Sem PoC público CVE-2026-*** (Exchange) — CVEs post-auth (45504/55005/
  62913) exigem cred low-priv de mailbox, que não foi obtida.
- **IP real do Exchange não descoberto** (sem Shodan/Censys API key) —
  todos os testes OWA atravessam Cloudflare (WAF); IP real habilitaria
  bypass WAF + portscan direto (25/443/4172/8080) + re-teste de chains.
- **CRM sem emails de admin conhecidos** — sem dicionário de emails de
  gestores Seducar, cred-stuffing CRM não é viável.
- OWA login aceita email OU UPN (domínio NETBIOS). Testado só email format;
  UPN (ex. CENTRAL\igor.velazquez) não testado — baixo payoff adicional.
