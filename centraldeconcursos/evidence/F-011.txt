FINDING F-011 — Enumeração de escolas/tenants Seducar sem auth + paths S3 vazados (CRM backend)
==============================================================================

## Alvo / Host / Endpoint
- https://api-crm-h4ww.onrender.com/auth/user/school?domain=<tenant-domain> (GET, SEM auth)
- Backend CRM Seducar (AdonisJS on Render), referenciado pelo frontend
  crm.centraldeconcursos.com.br (Vue SPA, bundle /assets/index-S7rijOWh.js)

## Severidade: MÉDIA
Endpoint público (sem autenticação) retorna a configuração completa de
qualquer escola/tenant Seducar a partir do domínio informado, incluindo:
- ID interno do tenant, nome, domínio, cor de tema, classe CSS de tema;
- URLs de logotipos (desktop/mobile/CRM) apontando para o bucket S3
  COMPARTILHADO entre tenants (`files-producao.s3.us-east-2.amazonaws.com`)
  com prefixo de path por tenant (`central-de-concursos/`, `degrau-cultural/`).
Isso permite: (a) enumerar todos os clientes da plataforma Seducar (fuga de
info comercial / mapeamento de attack surface multi-tenant); (b) confirmar
que o CRM é multi-tenant compartilhado entre concorrentes (centraldeconcursos
e degraucultural no mesmo backend); (c) descobrir o bucket S3 real do alvo
(`files-producao`) que a fase cloud não havia encontrado (buscavam
`centraldeconcursos*`, mas o bucket é genérico `files-producao` com prefixo
de path por tenant).

## Output — tenants confirmados (sem auth)
| Tenant                | id | domain                       | theme-color | S3 prefix            |
|-----------------------|----|------------------------------|-------------|----------------------|
| Degrau Cultural       | 1  | degraucultural.com.br        | #009c73     | degrau-cultural/     |
| Central de Concursos  | 2  | centraldeconcursos.com.br    | #031af5     | central-de-concursos/ |

(O CRM backend provavelmente serve outros tenants Seducar — enumerável por
tentativa de domínios conhecidos.)

## S3 bucket confirmado (novo — não coberto pela fase cloud)
- `files-producao.s3.us-east-2.amazonaws.com` (região us-east-2)
  - Listing anônimo: NEGADO (403 AccessDenied) — ACL de bucket bloqueia list.
  - GET de objeto específico (logo/edital): 200 — objetos são public-read
    (intencional para mídia/logos/editais exibidos no site).
  - Prefixos por tenant: `central-de-concursos/`, `degrau-cultural/`.
  - Objetos sensíveis guessados (`.env`, `backup.zip`): 403 (não-encontrável
    sem listing; bloqueio adequado).
  - Risco: se algum objeto privado (documentos de alunos, backups) foi
    marcado como public-read por erro, estaria acessível — sem listing não
    é enumerável, mas a fase cloud deve validar object-level ACLs.

## Interpretação
1. **Enumeração de tenants sem auth:** O endpoint `/auth/user/school` é o
   "resolver de tenant" do CRM (usado pelo frontend para carregar a marca).
   Não exige autenticação e aceita qualquer domínio, retornando a config
   completa do tenant. Um atacante mapeia todos os clientes Seducar (e os
   IDs internos) — informação comercial sensível + facilita ataques
   cross-tenant (F-008).
2. **Bucket S3 compartilhado cross-tenant:** Os logos de central e degrau
   estão no MESMO bucket `files-producao` (prefixos distintos). Confirma
   infraestrutura multi-tenant compartilhada. A fase cloud não encontrou
   esse bucket porque buscou por nomes derivados do alvo (`centraldeconcursos*`);
   o bucket real é genérico (`files-producao`). Recomenda-se delegar à fase
   cloud a validação object-level desse bucket.
3. **Resolução de tenant por domínio (query param):** O CRM resolve tenant
   pelo parâmetro `domain` (ou pelo Host/Origin no fluxo normal). Isso é o
   vetor análogo ao F-006 (tenant por Origin) — separar tenant por input
   controlável é frágil; o isolamento deve vir do token autenticado.

## Impacto
- Fuga de lista de clientes Seducar (info comercial + attack surface).
- Confirmação de multi-tenancy compartilhado central↔degrau (mesmo backend
  CRM, mesmo bucket S3) — risco de cross-tenant se isolamento por token
  falhar.
- Bucket S3 real do alvo descoberto (`files-producao`) — abri validação
  object-level para a fase cloud.

## Recomendação
1. Exigir autenticação no endpoint `/auth/user/school` OU limitá-lo a
   domínios confiáveis via CORS/Origin + retornar apenas dados mínimos
   (logos), sem IDs internos.
2. Não expor IDs internos de tenant na resposta pública.
3. Validar object-level ACLs do bucket `files-producao.s3.us-east-2.
   amazonaws.com` — garantir que apenas objetos de mídia pública sejam
   public-read; documentos de alunos/backups devem ser privados (acesso
   via URL assinada).
4. Garantir que o isolamento de dados no CRM seja por claim de tenant do
   token (não pelo parâmetro `domain`).

## Próximo passo
- Enumerar mais domínios Seducar conhecidos (seducar.com.br já falhou;
  tentar outras escolas-brandeadas se lista de clientes for obtida via OSINT).
- Delegar à fase cloud: re-investigar bucket `files-producao` (object-level
  ACL, objetos sensíveis em `central-de-concursos/` como `backup*`, `*.env`,
  `alunos/`, `documentos/`).
