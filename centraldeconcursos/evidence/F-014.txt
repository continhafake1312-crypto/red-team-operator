FINDING F-014 — Signup público aberto sem captcha/verificação de email/CPF → token JWT imediato
==============================================================================

## Alvo / Host / Endpoint
- https://seducar-api-website.onrender.com/api/v1/auth/register (POST) — PROD
- https://seducar-api-website-hml.onrender.com/api/v1/auth/register (POST) — HML
- Backend Seducar (AdonisJS on Render), bypass WAF Cloudflare via Origin header (F-006)
- Backend HML exposto sem WAF (F-009)

## Severidade: BAIXA-MÉDIA
O endpoint `/api/v1/auth/register` aceita qualquer combinação de
`full_name + cpf (checksum válido) + password + email + cellphone` e cria
imediatamente uma conta de aluno retornando um token JWT válido por 7 dias,
SEM qualquer barreira anti-abuso:
- Sem CAPTCHA / reCAPTCHA / hCaptcha
- Sem verificação/validação de posse do email (não envia link de confirmação)
- Sem verificação de CPF contra base da Receita (apenas checksum de formato)
- Sem rate-limit perceptível no register (login tem rate-limit; register não)
- CPFs sintéticos (checksum válido mas não de pessoa real) são aceitos

Isso permite a um atacante (a) criar contas massivamente (spam/abuso de
recurso, database pollution), (b) obter tokens JWT válidos imediatos para
enumerar a superfície autenticada da API, (c) abusar de fluxos pós-cadastro
(trial/free content, carrinho, tickets). Não concede acesso admin nem dados
de outros usuários (isolamento intra-tenant confirmado efetivo — ver F-015),
mas habilita abuso operacional e enumeração autenticada.

## Observações
- Conta criada em HML (customer_id=1652206) e PROD (customer_id=1702468) — ambas
  com CPF/email sintéticos marcados como pentest. Nenhuma transação financeira
  realizada, nenhum dado de terceiro acessado (non-destrutivo).
- O `customer_id` PROD (1702468) próximo ao HML (1652206) sugere DBs separados
  mas com sequências similares (não compartilham IDs).
- Token HS256 — chave simétrica no servidor; não quebrável offline sem leak.
- Mass assignment testado: campos `role`/`isAdmin`/`school_id`/`is_admin`/
  `admin`/`permissions` enviados no body do register foram IGNORES — a conta
  criada manteve school_id=2 (central) e passport=false (não admin). Mass
  assignment BLOQUEADO (bom controle).

## Impacto
- Criação massiva de contas sem barreira (spam, database pollution, abuso de
  trial/free content).
- Enumeração autenticada da superfície /api/v1/* com token low-priv imediato
  (vetor usado neste engagement para validar isolamento intra/cross-tenant — F-015).
- Potencial abuso de fluxos pós-cadastro: carrinho, tickets, free content.
- NÃO concede acesso admin, NÃO acessa dados de outros usuários (isolamento
  confirmado efetivo — ver F-015), NÃO é foothold no Exchange.

## Recomendação
1. Adicionar CAPTCHA (reCAPTCHA Enterprise / hCaptcha) no endpoint de registro.
2. Verificar posse do email antes de ativar a conta (enviar link de confirmação;
   account em estado "pending" sem token até confirmação).
3. Validar CPF contra a base da Receita Federal (não apenas checksum de formato)
   OU exigir documento; ou aceitar CPF só após validação de email/telefone.
4. Rate-limitar o endpoint de registro por IP E por fingerprint (device/IP+UA).
5. Monitorar criação de contas em massa (detecção de burst por IP/domínio).
6. Não retornar token JWT imediatamente se a conta exigir verificação (atrasar
   o token até confirmação).
