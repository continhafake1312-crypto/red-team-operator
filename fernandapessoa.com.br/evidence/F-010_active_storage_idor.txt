# F-010 IDOR/BOLA — Rails Active Storage unauthenticated file access via leaked signed IDs
Alvo: api.youbiz.com.br (Cloudflare R2 backend: youbiz-storage.1b8f3f497ae032270837530aaa0cce8d.r2.cloudflarestorage.com)
Severidade: Alta
Timestamp: 2026-08-27T16:24:00Z

## Reprodução

O endpoint Rails Active Storage redirect NÃO exige autenticação:

    GET https://api.youbiz.com.br/rails/active_storage/blobs/redirect/<signed_id>/<filename>

Retorna HTTP 302 para URL pré-assinada do bucket Cloudflare R2, e seguindo o
redirect o arquivo é entregue diretamente.

Os `signed_id` são vazados via payload React Server Components (RSC) da página
pública inicial de `app.fernandapessoa.com.br` (Next.js), que renderiza no
servidor URLs completas do Active Storage no HTML/JSON do RSC.

Formato do signed_id (base64 + HMAC SHA1):
    {"_rails":{"data":"<UUID-blob_id>","pur":"blob_id"}}--<40-hex-hmac>

## Interpretação

- O endpoint `/rails/active_storage/blobs/redirect/` NÃO valida sessão/JWT — qualquer
  portador de um signed_id válido obtém o arquivo.
- Os signed_ids são HMAC-assinados (não forjáveis sem o `secret_key_base`), MAS são
  vazados em massa no payload RSC da home pública do Next.js, que inclui URLs de
  Active Storage completas (logo, imagens de conteúdo, etc.).
- A combinação (endpoint unauth + leak de signed_ids via RSC) = exposição de
  arquivos armazenados sem qualquer conta/autenticação.
- Os 3 arquivos confirmados são imagens de conteúdo (baixa sensibilidade), mas o
  MESMO padrão se aplica a qualquer arquivo (certificados, documentos de alunos,
  comprovantes de pagamento, materiais) cujo signed_id apareça em qualquer página
  ou resposta RSC acessível ao atacante.

## Impacto

- Acesso não-autenticado a arquivos privados do storage (Cloudflare R2).
- Potencial vazamento de documentos sensíveis (certificados, comprovantes,
  materiais de aula, documentos pessoais de alunos) dependendo de quais
  signed_ids sejam expostos nas páginas públicas/RSC do app.
- Confirmação do padrão BOLA: o "autorizador" é apenas a posse do signed_id, que
  vaza client-side.

## Recomendação

1. exigir autenticação (validar sessão/JWT do dono do blob) no endpoint
   `/rails/active_storage/blobs/redirect/` e `/representations/`.
2. NÃO serializar URLs de Active Storage com signed_ids em payloads RSC/HTML
   públicos; usar URLs temporárias server-side e verificar permissão por request.
3. Configurar `config.active_storage.routes_prefix` ou remover rotas públicas de
   Active Storage do namespace exposto.
4. Revisar o bucket R2: garantir que objetos não sejam públicos e que todas as
   requisições passem pelo backend autenticado.
5. Rotar o `secret_key_base` (mitigação de forge, embora o leak via RSC seja o
   vetor real).

### Interpretação do deep-dive

- Os 3 signed_ids são serializados no **layout global** (header/footer) da app
  Next.js (logo no `<link rel=icon>` + 2 imagens hero da landpage). Todas as
  páginas públicas compartilham o mesmo layout → sempre os mesmos 3.
- As rotas que poderiam servir **documentos sensíveis** (`/cursos`, `/manager`,
  `/api/cursos/<id>`, certificados, matrículas, comprovantes) exigem autenticação:
  respondem `NEXT_REDIRECT;replace;/login;307;` no payload RSC. Logo, seus
  signed_ids NÃO são serializados para um cliente anônimo.
- `/rails/active_storage/representations/<sid>/<variation_key>/<file>` → 404
  (variant endpoint exige variation_key HMAC-assinado; sem forge sem
  `secret_key_base`).
- Backend real `youbiz.onrender.com` (Render free tier) → 404 / dead (sleeping).
- `app-prd.youbiz.com.br` (callback URL vista no RSC) → TCP 000 (DNS/inacessível).

### Conclusão de severidade — MANTIDA em Alta (NÃO escalada para Crítica)

NÃO foram encontrados signed_ids de documentos sensíveis (certificados, PII,
comprovantes, materiais) em nenhuma rota pública. O vazamento de signed_ids
limita-se a 3 imagens de **baixa sensibilidade** (logo + 2 hero genéricas).
Para acessar signed_ids de documentos privados seria necessário:
(a) uma conta autenticada no app, ou (b) um vetor de forge (que exigiria
`secret_key_base`, não obtido).

F-010 permanece **Alta** (IDOR/BOLA real, mas impacto confirmado = imagens
públicas de conteúdo). Escalonamento para Crítica fica **condicional** à
obtenção de auth ou leak do `secret_key_base`.
