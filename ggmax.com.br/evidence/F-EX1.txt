## Contexto
JWT regular obtido em recon (test@test.com/test, sub=270, role Regular). Enum (F-E5):
`/protected` é admin-only (403 com JWT regular), role é DB-side (lookup por `sub`), e o
MESMO secret assina access+refresh. Hipótese: se o secret for fraco, quebrá-lo permite
forjar JWT com `sub`=admin_id (thyoity@gmail.com, id provavelmente baixo) → role=Admin no
DB → acesso /protected e, potencialmente, escalação.

## Análise
- O secret NÃO está no rockyou (14.3M) nem em mutações derivadas do engagement (4.780).
- Conclusão: o JWT_SECRET é uma string aleatória forte (provável config NestJS
  `JWT_SECRET` de 32+ bytes), não palavra de dicionário nem derivável do contexto.
- `alg:none` já testado pelo enum (BLOCKED). Header não tem `kid` (sem kid/JWK injection).
- Sem o secret, não há como forjar JWT admin. Vetor morto.

## Observação importante (escopo)
Mesmo QUEBRANDO o secret, o enum (ENUM.md §4.2) observa que `/adm/*` usa auth admin
SEPARADA com TOTP (POST /adm/auth → validation → POST /adm/auth/confirm com TOTP). Logo,
forjar o JWT regular daria acesso a `/protected` (admin-only regular) mas NÃO aos
endpoints `/adm/*` (que exigem admin JWT obtido via TOTP). Ainda assim seria confirmação
de escalação de privilégio.

## Impacto
NENHUM no estado atual. Escalação via JWT forgery não é factível sem o secret.

## Recomendação
1. Manter JWT_SECRET como secret aleatório forte (já está) — rotacionar periodicamente.
2. Adicionar `role` ao JWT claim (em vez de lookup DB-side só por `sub`) com verificação
   server-side, para que mesmo um JWT forjado não conceda role sem o claim assinado
   (defesa em profundidade caso o secret vaze um dia).
3. Não logar/expor o secret em client-side (confirmar que é server-side only).
