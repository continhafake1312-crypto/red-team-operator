## Contexto
Recon passivo/ativo (F-A11) testou SSRF imgproxy com canary EXTERNO e negou (allowlist
bloqueia fetch outbound). A hipótese do CVE-2025-24354: o endereço `0.0.0.0` bypassa o
check `IsLoopback()` (que só casa 127.0.0.0/8) e atinge serviços LOCAIS mesmo com allowlist.
Versões vulneráveis: imgproxy < 3.27.2.

## Reprodução exata (proxychains4 + HTTPS bypass CF + Tor)

### 1) imgproxy confirmado ativo
```
/health -> 200 "imgproxy is running" (19 bytes)
/       -> 404 "Invalid URL" (11 bytes)
/format -> 400 "Source is unreachable" (21 bytes)  <- imgproxy processa paths
```
Formato de source aceito: `/plain/{url}` (NÃO `/unsafe/` — este retorna "Invalid URL",
unsafe mode DESATIVADO). Baseline externo:
```
/plain/http://example.com/image.jpg -> 403 "Source is unreachable" (21 bytes)
```

## Análise
- TODOS os sources (loopback, private, docker-gateway, **próprio IP público do host**,
  file://, gopher://, s3://, externo, porta fechada) retornam a string genérica
  "Source is unreachable" [403 size=21] com timing idêntico (~2s, dominado pelo Tor).
- O `0.0.0.0` NÃO produz resposta distinta de uma porta fechada (:9999) → indica que o
  fetch NÃO chega a acontecer (rejeição em estágio pré-fetch pela proteção SSRF do
  imgproxy), não "alcançou nginx mas falhou em decodificar".
- imgproxy está em configuração locked-down: `/unsafe/` desativado, e proteção SSRF
  bloqueia 0.0.0.0/loopback/private/own-IP uniformemente. Ou é versão patched (>=3.27.2)
  ou a proteção sempre incluiu 0.0.0.0. Egress externo também bloqueado (example.com falha).
- Mesmo o `0.0.0.0` (núcleo do CVE-2025-24354) não contorna a proteção.

## Impacto
NENHUM. SSRF via 0.0.0.0 NÃO é explorável. Não há como atingir Meilisearch/Docker/Redis/
nginx internos através do imgproxy. (Pivoting interno via imgproxy descartado.)

## Recomendação
1. Manter imgproxy atualizado (>=3.27.2) e `/unsafe/` desativado (já está).
2. Restringir img-origin.ggmax.com.br a não expor o imgproxy sem WAF (origin direto).
3. Confirmar que `IMGPROXY_ALLOWED_SOURCES` está definido (deny-by-default) e que egress
   externo do container imgproxy é bloqueado (já observado).
