# F-009 jvmtiAgentLoad RCE primitive FUNCTIONAL in read-only JMX — CVE-2020-9004 chain blocker analysis
Alvo: video02.soultv.com.br (160.202.130.243) — JMX RMI 8085/8084, Wowza SE 4.8.0 (roda como root)
Severidade: **Crítica** (primitive de RCE confirmado; chain completa bloqueada por file-write)
Status: **Primitive VALIDADO; RCE completo NÃO alcançado (bloqueado por file-write primitive ausente)**
Timestamp: 2026-08-27T17:11:00Z (Fase 7b — exploit)

## Sumário
O MBean `com.sun.management:type=DiagnosticCommand` exposto no JMX read-only (cred default
`admin:admin`, ver F-E01) oferece a operação `jvmtiAgentLoad([Ljava.lang.String;)`. Validamos
**não-destrutivamente** que esta operação É INVOCÁVEL a partir do role read-only (nenhuma
SecurityException) — ou seja, **o primitive de RCE root está funcional**. Carregar um agente
JVMTI (nativo `.so` ou JAR `Agent-Class`) executa código nativo/Java **no processo do Wowza,
que roda como `root`** (user.name=root confirmado em F-E01).

A chain **completa** para RCE root está **bloqueada** por um único faltante: um **primitive de
escrita de arquivo** que coloque um agente binário (`.so` ou `.jar`) no filesystem do servidor.
Mapeamos TODAS as superfícies de escrita externas e nenhuma está disponível (ver seção
"Blocker analysis"). Logo, RCE root a partir da internet **não é alcançável** com os primitives
atuais — exige pivoting interno, cred Manager/REST, ou um file-write primitive adicional.

## Confirmação não-destrutiva — jvmtiAgentLoad invocável (sem permission-block)
Cliente Java RMI (JmxAgentLoad.java) via Tor socks5 + redirect localhost→IP real, conectado
ao registry JMX na porta 8085 (`/jmxrmi`) com cred `admin:admin` (read-only):

```
$ java JmxAgentLoad 160.202.130.243 8085 admin admin
[+] CONNECTED as admin:admin
[*] MBean count: 2485 domains: [JMImplementation, java.util.logging, java.lang, com.sun.management, WowzaStreamingEngine, java.nio]

=== ALL DiagnosticCommand operations ===
  java.lang.String jvmtiAgentLoad([Ljava.lang.String; arguments)  impact=ACTION_INFO
  java.lang.String vmInfo() / vmUptime() / vmVersion() / vmCommandLine() / vmSystemProperties()
  java.lang.String vmDynlibs() / vmClassHierarchy() / gcClassHistogram() / gcRun() / ...
  (33 ops total — DiagnosticCommand HotSpot full surface)

=== jvmtiAgentLoad test 1: nonexistent .so path ===
  RETURNED (no exception): 
  >>> PRIMITIVE FUNCTIONAL (no permission block) — file path accepted
=== jvmtiAgentLoad test 2: nonexistent .jar path ===
  RETURNED: 100                       (erro de carga do agent — código 100, sem exception)
=== jvmtiAgentLoad test 3: remote http:// URL ===
  RETURNED: 100                       (URL tratada como path local — não suporta HTTP; falha sem exception)
```

**Interpretação:** em todas as 3 tentativas a operação **retornou sem SecurityException**. Um
role read-only que bloqueasse `invoke` de ops sensíveis teria lançado `SecurityException` /
"Invalid access level" (como ocorre com `createMBean` — ver F-E01 / role characterization). O
retorno "100" é o código de erro interno do carregador de agent (path inexistente), **não** um
bloqueio de permissão. Conclusão: **o primitive jvmtiAgentLoad está desbloqueado no role
read-only** — apenas falta um arquivo agent válido no FS.

> Observação sobre `http://` (test 3): o carregador de agent JVMTI trata o argumento como
> path de arquivo local (dlopen p/ .so, open zip p/ .jar); **não suporta URLs HTTP**. Logo a
> técnica "carregar agent JAR remoto via HTTP" **não é viável** neste primitive — o agent tem
> de residir no filesystem do servidor.

## Chain CVE-2020-9004 (read-only → ativar JMX unauth → restart → JMX readwrite → MLet RCE)
- **Pré-condição:** 1 cred válida no Manager (read-only basta) para POST em endpoint admin
  que habilita JMX unauth + restart.
- **Status: BLOQUEADA no passo de cred.** Manager 8088 + REST 8087: **nenhum cred válido**
  após brute focado (96 + 40 combos) — ver F-010. Sem cred read-only no Manager, não há como
  acionar o bypass de autorização do CVE-2020-9004.
- Mesmo se JMX unauth fosse habilitado, o registry 8085/8084 já é alcançável (F-E01), então
  readwrite via MLet `createMBean` (URL remota) → RCE root seria viável APÓS obter a cred.

## Caminho alternativo (jvmtiAgentLoad) — status
- Primitive **funcional** (confirmado). Faltante: **file-write primitive** para colocar agent
  binário no FS. Nenhuma superfície externa de escrita disponível (tabela acima).
- Único candidato restante: `writeAppConfig`/`writeAppInstConfig` via JMX — porém escrevem
  XML em path `.xml` fixo (não binário) e invocação é destrutiva (modifica config). Mesmo se
  funcional, **não entrega um .so/.jar** → não completa a chain jvmtiAgentLoad.

## Correção do F-005 (importante)
A seção "Fase 7b" do F-005 concluiu que o JMX NÃO é explorável porque o MBean server estaria em
host interno `18.231.132.245`. **ESSA CONCLUSÃO ESTÁ INCORRETA:**
1. O próprio F-005 (linhas 24-39) já demonstrou que `18.231.132.245` é o **echo do IP de saída
   do Tor** (muda a cada circuito) — não é infraestrutura do alvo.
2. A "Fase 7b" usou `JmxProbe`/`RmiDump` na porta **8084** (rmiConnectionPort) e obteve
   `NoSuchObjectException` — porta errada. O registry correto é **8085** (rmiRegistryPort,
   binding `/jmxrmi`).
3. Conexão via 8085 com `admin:admin` **funciona** (F-E01 enumerou 2446 MBeans; este finding
   F-009 conectou e invocou jvmtiAgentLoad com sucesso).
4. **JMX É alcançável e explorável em read-only** — o primitive de RCE está confirmado.
5. O **verdadeiro blocker** do RCE root é a **ausência de cred Manager/REST + ausência de
   file-write primitive externo**, NÃO a "não-alcançabilidade do JMX".

## Impacto
- **Crítico (potencial):** primitive de RCE root confirmado (jvmtiAgentLoad invocável em
  read-only + Wowza roda como root). Qualquer atacante que obtenha UM file-write primitive
  (ou 1 cred read-only no Manager p/ chain CVE-2020-9004) obtém **RCE root** no video02.
- **Atual (sem cred/file-write):** disclosure crítico já confirmado em F-E01 (root, OS,
  licença crackeada, 46 clientes IPTV, paths, GUIDs) + primitive de RCE latente.

## Recomendação
1. **Remover cred default do JMX** — trocar `admin:admin` (jmxremote.password) por segredo
   forte; ou desabilitar JMX remoto (`com.sun.management.jmxremote=false`) / restringir a
   localhost + firewall.
2. **Fechar 8084/8085 à internet** (security group) — JMX/RMI nunca deve ser exposto.
3. **Atualizar Wowza 4.8.0 → ≥4.9.1** (fix CVE-2020-9004, CVE-2024-52052/52053/52055,
  CVE-2021-31539). 4.8.0 + licença crackeada (zedays.co) é risco crítico (possível backdoor).
4. **Restringir primitive `jvmtiAgentLoad`** — idealmente o role read-only não deveria invocar
   DiagnosticCommand write-ops; revisar a config de access do JMX.
5. Rotear todo write HTTP por auth (nenhum endpoint de upload unauth).
