# F-011 Firebase Cloud Function `getPaymentToken` — proxy UNAUTH para Stripe token creation (payment surface)
Alvo: https://us-central1-tv-iteractiva.cloudfunctions.net/getPaymentToken (GCP Firebase, sem Cloudflare)
Severidade: **Alta** (superfície de pagamento sem auth — token minting / carding oracle)
Status: **Confirmado (read-only — apenas erros da API Stripe capturados; NENHUM token real mintado)**
Timestamp: 2026-08-27T17:16:00Z (Fase 7b — exploit)

## Sumário
A Cloud Function `getPaymentToken` (projeto Firebase `tv-iteractiva`, mesma config vazada de
P-FIND-P02) aceita POSTs **sem qualquer autenticação** e os encaminha diretamente à API de
criação de tokens da Stripe (em nome da conta Stripe da Soul TV). A função retorna os erros
da API Stripe **sem filtragem**, provando ser um proxy cego de tokenização. Com um número de
cartão válido, um atacante poderia **mintar tokens Stripe sem auth** — permitindo carding
(oráculo de validação de cartão), abuso do fluxo de pagamento e potencial bypass de 3DS / do
fluxo legítimo de checkout.

## Confirmação (não-destrutiva — dados fictícios, sem token real)
```
--- GET (no body) ---
HTTP/2 405
content-type: application/json; charset=utf-8
{"message":"Method not allowed"}
  # Função existe; aceita POST.

--- POST cartão fictício (PAN de teste 4111..., exp futuro, cvc fictício) ---
HTTP/2 400
content-type: application/json; charset=utf-8
{"code":"parameter_missing","message":"Missing required param: card[exp_month]."}
  # Erro da API Stripe repassado DIRETAMENTE → a função encaminhou o POST à Stripe sem auth.
  # Com `card[exp_month]` etc. válidos a Stripe mintaria um token (não testado — escopo read-only).

--- POST empty {} ---
HTTP/2 400
{"code":"parameter_missing","message":"You must supply either a card, customer, PII data,
  bank account, or account legal entity to create a token. ... See the API reference:
  https://stripe.com/docs/api#token_object"}
  # Mensagem completa da API de `tokens` da Stripe (Stripe.js/Token creation) — confirma o
  # endpoint ser um proxy ao `POST /v1/tokens` da Stripe usando a secret key do projeto.
```
- `access-control-allow-origin: *` → aceita chamadas cross-origin de qualquer site.
- `server: Google Frontend` → Firebase Cloud Function (GCP), não protegido por Cloudflare
  (IP/rota direta do GCP) — não há WAF intermediário.

## Impacto
- **Token minting sem auth:** qualquer atacante pode submeter dados de cartão à Stripe em
  nome da Soul TV e obter tokens Stripe (`tok_...`) — tokens representam dados de cartão
  (PII financeira), usáveis para cobrança via a API da Soul TV ou outros endpoints que
  aceitem tokens da conta.
- **Carding oracle:** a função pode ser usada para testar validade de PANs (cartões roubados)
  via respostas de erro da Stripe (`card_declined`, `incorrect_number`, `expired_card`)
  — útil a fraudadores para validar cartões em massa (risk para o merchant: chargebacks,
  flag de fraude na conta Stripe, possível bloqueio da conta).
- **Bypass do fluxo de checkout legítimo:** o frontend (pay.soultv) normalmente chama esta
  função após auth/CAPTCHA; exposta sem auth, o atacante invoca diretamente.
- **CORS `*`:** permite acionamento cross-origin de sites maliciosos (cartão de terceiros
  submetido por JS no navegador de vítima — embora normalmente precise do PAN).
- NÃO há rate-limiting visível (Firebase default); abuso massivo é viável.

## Notas
- O endpoint NÃO minta dinheiro diretamente — Stripe tokens são one-use e representam dados
  de cartão, não uma cobrança. Cobrança efetiva exigiria outro endpoint (ex.: cobrança server-
  side com a secret key). Mas a tokenização sem auth já é uma superfície de pagamento grave.
- Não mintamos nenhum token real (dados fictícios de teste apenas capturaram erros), em
  conformidade com o escopo read-only e a proibição de completar transações.

## Recomendação
1. **Autenticar a Cloud Function** — exigir Firebase Auth (token JWT do usuário autenticado) +
   verificar claims antes de chamar a Stripe. Idealmente, mover a criação de token para um
   fluxo server-side com auth + rate-limit + CAPTCHA.
2. **Validação de origem (CORS):** trocar `access-control-allow-origin: *` por whitelist dos
   domínios `*.soultv.com.br`.
3. **Rate-limiting** (Firebase App Check + quotas por IP) para impedir carding em massa.
4. **Não repassar erros da Stripe** ao cliente — normalizar mensagens para não revelar o
   motivo exato do declínio (oráculo de carding).
5. Usar Stripe Radar / 3DS para reduzir fraude; monitorar picos de criação de tokens.
6. Rotacionar/revisar a Stripe secret key se houver suspeita de abuso.
