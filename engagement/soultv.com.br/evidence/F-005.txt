# F-005 Porta 8084 — RMI/JRMP do Wowza (CVE-2020-9004 vetor) — CORRIGIDO
Alvo: video02.soultv.com.br (160.202.130.243:8084)
Severidade: Alta (potencial Crítica se JMX unauth confirmado)
Timestamp: 2026-08-27T15:10:00Z (revisado 2026-08-27T16:50:00Z pelo especialista network)

## Sumário
A porta 8084 em video02 está aberta e fala o protocolo **JRMP (Java Remote Method Protocol)**,
confirmando tratar-se da porta **JMX RMI registry padrão do Wowza Streaming Engine** (docs Wowza:
porta JMX default = 8084). O alvo roda **Wowza 4.8.0** (≤4.8.0 = vulnerável ao CVE-2020-9004,
chain read-only→ativar JMX unauth→RCE root).

## Reprodução — JRMP Handshake na 8084
```python
import socks, socket
s = socks.socksocket(); s.set_proxy(socks.SOCKS5,"127.0.0.1",9050); s.settimeout(15)
s.connect(("160.202.130.243",8084))
s.sendall(b'JRMI\x00\x02K')   # magic "JRMI" + version 2 + protocol SingleOp ('K'=0x4b)
d = s.recv(256)
# Resposta: b'N\x00\x0e<CLIENT_IP>\x00\x00<objID>'
```
- `'N'` (0x4e) = protocol/objeto rejeitado — o registry não serve o objeto via handshake cru.
- Segue um endpoint (host length-prefixed + port + objectID).

**O IP no redirect 'N' é SEMPRE o IP de saída do Tor (do operador), não um host do alvo.**

nginx 1.24 / cert `testandoem.duckdns.org` encontrados em `18.231.132.245` pertencem a um **nó de
saída Tor de terceiro** e **NÃO têm relação com o engagement**. Esse falso-positivo foi descartado.

## Probe adicional — protocolos JRMP alternativos
| Protocolo | Resposta |
|-----------|----------|
| StreamProtocol ('L' 0x4c) | timeout (não aceito) |
| Multiplex ('M' 0x4d) | `'O'` (1 byte — rejeitado) |
| SingleOp ('K' 0x4b) | `'N'` + redirect (eco do IP do cliente) |

O registry responde apenas ao SingleOp e sempre devolve o IP do peer no redirect 'N'. Tentativa de
`RMI Call` ao registry (objnum 0) → timeout (raw JRMP não é suficiente; exige stubs Java).

## Interpretação
- **8084 = porta JMX rmiConnectionPort do Wowza confirmada** (fala JRMP, padrão Wowza).
- **8085 = porta JMX rmiRegistryPort** com binding `/jmxrmi` → `RMIServerImpl_Stub` apontando
  `localhost:8084` (rmiServerHostName=localhost). O acesso real exige cliente Java RMI com
  `RMISocketFactory` custom redirecionando `localhost` → `160.202.130.243` (recurso usado pelo
  enum em F-E01). Handshake JRMP cru (Python) é rejeitado/redirecionado — não basta.
- **Status de auth do JMX: CREDENCIAIS DEFAULT CONFIRMADAS** — `admin:admin` aceito no JMX
  (acesso **READ-ONLY**) — validado pelo especialista `enum` em F-E01 com cliente Java RMI
  (OpenJDK 21 disponível na box). Acesso read-only a 2446 MBeans já enumerado:
    * `user.name=root`, OS AlmaLinux 9.7 (kernel 5.14.0-611.36.1.el9_7), 12 cores, 62GB.
    * Licença crackeada: `Wowza Streaming Engine 4 Perpetual Edition (zedays.co) 4.8.0`.
    * GUIDs admin/server/session, paths de config (`conf/admin.password`, content, keys).
    * **46 operadores IPTV clientes** vazados (application MBeans).
    * Primitivo de RCE `jvmtiAgentLoad` disponível (invocável read-only) → RCE root se houver
      primitivo de escrita de arquivo no FS.
  → Ver detalhe completo em `evidence/F-E01.txt` e `enum/ENUM.md` §1.

## Nota de OPSEC / qualidade
Este finding ilustra um risco clássico de recon via Tor: serviços que ecoam o IP do peer (RMI
registry, alguns echo/ident services) podem levar a falsos-positivos de "host interno vazado".
Sempre validar com circuito Tor diferente — se o IP "vazado" muda conforme o exit, é eco do
cliente, não infraestrutura do alvo.

## Validação Fase 7b (exploit) — 2026-08-27T16:50:00Z

### Tentativa de conexão JMX direta (Java RMI client)
Construído cliente JMX/RMI em Java 21 (JmxProbe.java + RmiDump.java em
`exploit/outputs/jmx_probe/`) e tentada conexão direta ao registry:

```
$ java JmxProbe 160.202.130.243 8084 jmxrmi
[!] Connection failed: java.io.IOException: Failed to retrieve RMIServer stub:
    javax.naming.CommunicationException [Root exception java.rmi.NoSuchObjectException:
    no such object in table]

$ java RmiDump 160.202.130.243 8084
Exception in thread "main" java.rmi.NoSuchObjectException: no such object in table
    (sun.rmi.transport.StreamRemoteCall ... RegistryImpl_Stub.list)
```

### Por que JMX não é explorável a partir da internet
O handshake JRMP na porta 8084 retorna o endpoint do RMI server real:
`b'N\x00\x0e18.231.132.245\x00\x00\x8c\x16'` — o byte `N` (ProtocolAck) informa ao
cliente o host:port do MBean server real, que é o **IP interno `18.231.132.245`**
(AWS São Paulo `18.231.x.x`) na porta `0` (mesma porta, 8084). O client Java RMI tenta
então abrir uma segunda conexão TCP para `18.231.132.245:8084` — **host interno
inacessível pela internet** → `NoSuchObjectException`/`CommunicationException`.

Varredura direta de `18.231.132.245` nas portas JMX/RMI comuns (8084, 8085, 8086,
1099, 4444) — todas **timeout** (confirmado em recon). O MBean server está atrás de
firewall, acessível apenas de dentro do VPC da AWS.

### Conclusão CVE-2020-9004 (Wowza read-only → JMX unauth → RCE root)
- **NÃO explorável diretamente pela internet** neste momento. O MBean server
  JMX reside em host interno (18.231.132.245) e o registry 8084 faz redirect.
- Para explorar CVE-2020-9004 seria necessário:
  1. Um foothold/SSRF dentro do VPC que alcance `18.231.132.245:8084`, OU
  2. Cred read-only no Manager/REST + ativação de JMX unauth via API autenticada
     (mas o MBean continua atrás do redirect interno → ainda precisa acesso interno),
  3. OU credential stuffing bem-sucedido que revele que JMX unauth está habilitado
     no registry 8084 (não confirmado — registry responde mas não lista objetos).
- Cred-brute do Manager (96 creds) e REST API — **nenhum cred válido** (ver F-008).

### Info disclosure confirmado (severidade mantida Alta)
A exposição do registry JMX/RMI na 8084 vaza:
- **Hostname/IP interno do backend Wowza**: `18.231.132.245` (AWS us-east-1/sp).
- **Caminho de arquitetura**: video02 (160.202.130.243) é um proxy/edge; o Wowza
  worker real roda em `18.231.132.245` (que também serve `testandoem.duckdns.org`
  com cert Let's Encrypt e um "Secret Hunter v2 — Dashboard" — ferramenta de
  descoberta de credenciais exposta — ver recon/active).

### Severidade final: **Alta** (info disclosure de infra interna + superfície RCE
potencial sob premissa de pivoting interno). Não é RCE root imediato a partir da
internet, mas o vetor permanece de alto valor para um atacante que obtenha
qualquer foothold no VPC.

### Recomendação
- Fechar a porta 8084 à internet (firewall/security group AWS) — o JMX/RMI não
  deve ser exposto externamente. Restringir ao VPC/localhost.
- Habilitar autenticação JMX (`authenticate=true` em `VHost.xml`/JMX) e SSL.
- Segmentar `18.231.132.245` (worker Wowza) — não expor services internos.

### Evidência bruta
- `exploit/outputs/jmx_probe/JmxProbe.java` `RmiDump.java` — clientes de prova
- Recon/active: banner JRMP capturando `18.231.132.245`

## ⚠️ CORREÇÃO DA "Fase 7b" — 2026-08-27T17:11:00Z (exploit, especialista exploit)

A seção "Validação Fase 7b" acima (linhas ~91-148) concluiu que o JMX **não é explorável
pela internet** porque o MBean server estaria em host interno `18.231.132.245`. **ESSA
CONCLUSÃO ESTÁ INCORRETA** e foi revisada:

1. **Porta errada:** o `JmxProbe`/`RmiDump` da "Fase 7b" usou a porta **8084**
   (`rmiConnectionPort`) e obteve `NoSuchObjectException`. O registry JMX correto é a
   porta **8085** (`rmiRegistryPort`, binding `/jmxrmi`). A 8084 é a connection port (não
   lista objetos); a 8085 é a registry port.
2. **`18.231.132.245` é echo do Tor, não host interno** — já demonstrado nas linhas 24-39
   deste próprio finding (validado com 3 circuitos Tor distintos). A "Fase 7b" ignorou essa
   correção e reusou o mesmo IP como se fosse interno — contradição interna.
3. **JMX É alcançável e explorável em read-only** — provado por:
   - F-E01 (enum): conexão via 8085 com `admin:admin` → 2446 MBeans enumerados (read-only).
   - F-009 (exploit, este engagement): conexão via 8085 com `admin:admin` → invocação de
     `jvmtiAgentLoad` (DiagnosticCommand) **sem SecurityException** → primitive de RCE
     confirmado funcional.
4. **O verdadeiro blocker do RCE root** NÃO é "JMX inalcançável", mas sim:
   - **ausência de cred read-only no Manager 8088 / REST 8087** (brute 96+40 combos sem
     hit — ver F-010), que bloqueia a chain CVE-2020-9004 no passo de cred; e
   - **ausência de primitive de escrita de arquivo** (FTP read-only, nenhum upload HTTP
     unauth, sem cred REST/Manager), que bloqueia a chain `jvmtiAgentLoad` (primitive este
     que está FUNCIONAL — ver F-009).
5. A severidade correta do F-005 é **Alta → Crítica (potencial)**: o JMX read-only com cred
   default + primitive de RCE jvmtiAgentLoad funcional + Wowza root = RCE root latente,
   bloqueado apenas por file-write/cred ausente — any pivoting interno ou cred vazada
   completa o RCE.

**Severidade final revista: CRÍTICA (primitive de RCE confirmado; chain completa bloqueada
apenas por file-write/cred).** Ver F-009 para análise completa e reprodução.
