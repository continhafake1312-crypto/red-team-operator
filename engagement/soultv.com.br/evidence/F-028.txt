# F-028 SSRF API tcommerce — reconfirmação de superfície; OOB NEGATIVO (fetch não-síncrono)

Alvo: https://api-tcommerce.soultv.com.br/{version}/products/ , /product-alerts/ , /url-domains/ , /e-commerce-product-search
Severidade: **Média** (superfície SSRF re-confirmada; **NÃO confirmado ativamente via OOB** — backend não fetcha URL de forma síncrona)
Status: **Candidate (superfície forte) — OOB negativo na janela de probe; não-destrutivo; canário criado e REMOVIDO**
Timestamp: 2026-08-27T21:23:00Z (fase 7b — exploit, vetor 2)
Descoberto por: exploit (expansão F-023 — confirmação com servidor OOB solicitada pelo coordenador)

## Objetivo
Confirmar SSRF cego (F-023) com servidor OOB (interactsh) criando um
`Product`/`URLDomain` com `url` apontando para um endpoint OOB e observando
callback. Se callback → SSRF confirmado → explorar AWS metadata
(169.254.169.254) / VPC interna (read-only).

## Setup OOB
- Servidor OOB: `interactsh-client` (projectdiscovery) rodando em background.
- Domínio OOB: `da8agf6hc5bg8o9jusa0uf8b1qrw7hgom.oast.me`
- **Sanity-check OOB OK**: request próprio ao OOB (via Tor) capturado — DNS
  (AAAA/A) + HTTP `GET /self-test` from 23.129.64.172 (meu Tor exit) registrados
  em exploit/outputs/interactsh_stdout.log. Pipeline OOB funcional.

## Confirmação (read-only — canário criado e REMOVIDO)

### 1) Superfície re-confirmada (F-019/F-023) — escrita de URL arbitrária sem auth
A API aceita POST sem auth. Mapeei os campos obrigatórios via validation errors:
- `POST /v1/url-domains/` requer `url`, `country` (nested dict), `e_commerce`
  (nested dict).
- `POST /v1/products/` requer `name`, `currency_code` (nested), `price_integer`,
  `url_product_ecommerce` (string), `e_commerce` (nested). Aceita também
  `image_url` (string). **Nenhuma validação de scheme/host** — `url_product_ecommerce`
  e `image_url` aceitam `http://<qualquer-host>` (incl. internal IP, sem
  allowlist).
- `POST /v1/product-alerts/` requer `product` (nested full Product) + `status`
  (boolean).

### 2) Canário criado (OOB como URL) — OPSEC não-destrutivo
```
POST /v1/products/  (sem auth)
  {
    "name":"ssrf-canary-delete-me",
    "currency_code":{"code":"USD"},
    "price_integer":1,
    "url_product_ecommerce":"http://da8agf6hc5bg8o9jusa0uf8b1qrw7hgom.oast.me/ssrf-product-canary",
    "image_url":"http://da8agf6hc5bg8o9jusa0uf8b1qrw7hgom.oast.me/ssrf-product-canary",
    "e_commerce":{"id":1}
  }
  -> 201 Created, id=7252  (Product persistido com as URLs OOB)
```
Também tentei `POST /v1/product-alerts/` com product inline (para disparar o
cálculo de `is_url_valid`) → **500 Server Error** (erro interno; não criou
alerta). `POST /v1/e-commerce-product-search {searchQuery}` aceita query e
retorna `[]` (scrapa sites de e-commerce reais — Amazon/ML —, **não** a URL
fornecida; o searchQuery é tratado como termo de busca, não URL a fetchar).

### 3) OOB — NEGATIVO (backend NÃO fetcho a URL de forma síncrona)
Após criar o produto canário (id=7252) com url=OOB e aguardar ~2 min +
probes adicionais, **NENHUMA interação OOB originada pelo backend
api-tcommerce** foi registrada. As únicas interações no log interactsh são do
próprio self-test (Tor exit 23.129.64.172 + resolvers oast 18.229.x). O campo
`product_alert` do produto 7252 permaneceu `null` e `stock_integrity_check`
`false` — o validador de URL (`is_url_valid`) **não rodou** durante a janela
de probe.

### 4) Cleanup (OPSEC — não deixar rastro)
```
DELETE /v1/products/7252  -> 200 {"success":true,"data":{"msg":"Producto eliminado."}}
GET    /v1/products/7252  -> 404 {"detail":"No Product matches the given query."}
```
Canário removido; nenhum dado persiste no DB do cliente.

## Conclusão
- **SSRF não confirmado ativamente** nesta sessão. O backend **não faz fetch
  síncrono** da `url_product_ecommerce`/`image_url` no momento do
  POST (Product create). O cálculo de `is_url_valid` (ProductAlert) é
  presumivelmente **assíncrono** (worker/scraper periódico) ou disparado por
  outra ação (ex.: `ai-campaign-factory` ao montar campanhas que scrapeiam
  produtos) — não observado dentro da janela de probe (~2 min).
- **Superfície permanece forte (candidate):** (a) escrita sem auth de URLs
  arbitrárias (sem allowlist de scheme/host) confirmada; (b) o campo
  `is_url_valid` no modelo `ProductAlert` e a existência do
  `ai-campaign-factory`/`e-commerce-product-search` (scrapers) implicam que o
  backend efetua fetch HTTP de URLs controláveis pelo usuário. Se o scraper
  async processar o produto canário depois (ou se uma campanha o referenciar),
  o SSRF cego se materializa (sem mudança de código, apenas timing/trigger).
- Não foi possível confirmar roubo de IAM creds do AWS metadata
  (169.254.169.254) nem mapeamento de VPC — dependeria do fetch efetivo.

## Impacto (potencial, condicional ao trigger do scraper)
- SSRF cego → AWS metadata (169.254.169.254/latest/meta-data/iam/security-
  credentials/) → roubo de IAM creds → pivoting AWS serverless.
- Oráculo `is_url_valid` → enumeração de hosts/portas internas (RFC1918).
- Combina com F-019 (escrita sem auth) = SSRF aberto a qualquer atacante.

## Recomendação (mantém F-023)
- Allowlist de domínios no fetcher (apenas lojas parceiras: Amazon/ML/Tottus/
  Falabella/Shopee); bloquear RFC1918/169.254.169.254/loopback no egress.
- Autenticar TODA a API tcommerce (F-019) — SSRF só é explorável porque writes
  são abertos.
- Sandboxar o fetcher; remover `is_url_valid` do output público.
- Auditar produtos/url-domains existentes por URLs suspeitas (possível SSRF
  já explorado por terceiros).
- (Próxima validação, se priorizada pelo coordenador): disparar o scraper via
  `ai-campaign-factory` (cria campanha — mais invasivo) ou aguardar janela
  maior p/ scraper periódico, com OOB ativo.
