# F-014 BOLA/IDOR não-autenticado — enumeração da base completa de assinantes (CMS API)
Alvo: https://cms.soultv.com.br/v1/account/{id}
Severidade: Crítica
Timestamp: 2026-08-27T17:10:00Z
Descoberto por: webapp (via análise do JS bundle pay: `getUserInfo`→`this.api.get("account/${Ie}")`)

## Sumário
O endpoint `GET /v1/account/{id}` retorna dados pessoais de qualquer assinante
a partir do seu ID sequencial, **SEM NENHUMA autenticação**. O ID é inteiro
sequencial começando em 1, então toda a base de clientes é enumerável por
incremento. Confirmamos IDs de 1 a 856437 (máximo atual) → **~856.000
assinantes** com dados pessoais expostos sem auth.

Dados vazados por registro: `id`, `email`, `full_name`, `first_name`,
`last_name`, `fb_id` (Facebook UID), `img` (URL de foto, às vezes Facebook
Graph ou S3 `tv-iteractiva-prod.s3.amazonaws.com`).

Este é o catálogo completo de clientes de um serviço de IPTV/streaming
(Soul TV), incluindo emails reais de clientes pagantes — superfície de
ataque direta para phishing, credential stuffing, fraude e venda de dados.

| full_name   | SIM      | nome completo |

## Impacto
- **Crítico**: vazamento massivo de PII de ~856K assinantes (LGPD Art. 7º — dado
  pessoal em posse do controlador exposto sem justificativa). Multa potencial
  ANPD: até 2% do faturamento, R$ 50M, ou sanções administrativas.
- Superfície direta para:
  - **credential stuffing** cruzando emails com leaks públicos (HaveIBeenPwned)
    + Firebase signInWithPassword (C-003) e CMS signin.
  - **phishing direcionado** ("Soul TV — confirme seu pagamento") com nome+email.
  - **account takeover via Facebook** — fb_id exposto pode ser usado em fluxos
    de OAuth/SSO se tokens FB forem obtidos por outros meios.
  - **correlação financeira**: combinar com F-015 (relatórios com `user_id`)
    para saber quem assina o quê, quanto paga e quando.
- Email enumeration confirmada: `{"success":false,"message":"O email já está
  registrado."}` ao tentar signup com email existente.

## Recomendação
1. **Autenticar** `GET /v1/account/{id}` — exigir token + verificar que o
   solicitante só pode acessar o próprio ID (authorization: `id == request.user.id`).
2. Nunca expor `email`/`full_name`/`fb_id` de outros usuários via API pública.
   Endpoints públicos devem retornar apenas dados necessários ao catálogo
   (ex.: nome do canal em `/v1/brand/{id}`).
3. Remover `/v1/account/{id}` público ou mover para admin-only com RBAC.
4. Rate limiting agressivo (max 30 req/min/IP) + CAPTCHA em qualquer endpoint
   que retorne dados de usuário.
5. Notificar ANPD (incidente de segurança com dados pessoais, LGPD Art. 48).
6. Auditoria de acesso: verificar logs por enumeracão em massa já ocorrida.
