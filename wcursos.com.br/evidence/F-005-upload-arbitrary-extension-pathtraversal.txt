## CHANGES vs the Fase-6 (webapp) write-up
The Fase-6 draft claimed "accepts arbitrary extension incl. .jsp -> POST OK (NOT
rejected)" and listed RCE as a candidate. Validation CORRECTS this:
  * The "POST OK" response is only a multipart-RECEIVE acknowledgement. It is
    returned for EVERY upload regardless of whether the file is actually persisted.
  * The companion /portal/verificaArquivoProfessor is the authoritative save
    confirmation. With it, executable/dangerous extensions are REJECTED on save:
      .jsp  -> status:-1 "O arquivo não foi salvo..."  (NOT persisted)
      .jspx -> status:-1 (NOT persisted)
      .war  -> status:-1 (NOT persisted)
      .sh   -> status:-1 (NOT persisted)
      .html/.htm/.svg -> status:-1 (NOT persisted)
      .txt  -> status:0  "anexado com sucesso"         (persisted)  [control]
      .png  -> status:0  (persisted)
  * The Fase-6 test used idUser=0 in verificaArquivoProfessor, which is why it
    incorrectly concluded the file "wasn't saved" — SILVANA's real idUser is 1721
    (read from /portal/perfil: "ID: 1721"). With idUser=1721 the round-trip
    fully succeeds (see below).
  * => The "arbitrary-extension upload -> RCE candidate" is REFUTED. There IS a
    server-side extension allow/blocklist enforced at persistence time; .jsp/.war/.sh
    are NOT written to disk. RCE via this endpoint is NOT achievable.

## What IS confirmed (real defects, retained at MEDIUM)

### (A) Round-trip upload->persist->retrieve CONFIRMED (authenticated, benign .txt)
Upload stores the file at <base>/<diretorio>/<submitted-filename>; the filename
includes a client-supplied idUser prefix (NOT re-prefixed with the session user):
  POST /portal/RecebeArquivo
    -F "file=@marker.txt;filename=1721.pt1787849835.txt" -F "diretorio=test" -F "delete=false"
  -> HTTP 200, 8 B, "POST OK"
  POST /portal/verificaArquivoProfessor
    directory=test&nameFile=pt1787849835.txt&idUser=1721
  -> {"status":0,"message":"O arquivo pt1787849835.txt foi anexado com sucesso."}
  GET /portal/dowloadArquivoTemp?directory=test&nameFile=pt1787849835.txt
  -> HTTP 200, 57 B, APPLICATION/OCTET-STREAM,
     Content-Disposition: attachment; filename=pt1787849835.txt
     body: "pentest benign marker file pt1787849835 - not executable"
  => File is persisted AND retrievable. dowloadArquivoTemp internally prepends the
     SESSION idUser (1721.) to resolve <base>/test/1721.<nameFile>.

### (B) Path-traversal in `diretorio` is HONORED on WRITE + READ (confirmed)
`diretorio` accepts `..` sequences and the file is saved at the traversed path and
retrievable with the same traversal:
  diretorio="."        -> verify status:0 (saved)
  diretorio=""         -> status:-1 (empty rejected)
  diretorio="../"      -> status:0 (saved — writes OUTSIDE base dir)  *** PATH TRAVERSAL ***
  diretorio="../../"   -> status:0
  diretorio="../../../"-> status:0
  diretorio="../ROOT"  -> status:0
  Each was confirmed via verificaArquivoProfessor with the matching directory value.
  => An authenticated user can write (allowlisted-extension) files to arbitrary
     traversed subpaths under/outside the configured upload base directory.

### (C) IDOR-on-write / cross-user upload namespace pollution (CONFIRMED, non-destructive)
The on-disk filename is the CLIENT-SUPPLIED filename AS-IS (the server does NOT
re-prefix with the session idUser). Uploading with a foreign idUser prefix writes
the file into THAT user's upload namespace:
  Upload: filename=9999.<uniq>.txt , diretorio=test (session user = 1721)
  -> POST OK
  verify idUser=9999 nameFile=<uniq>.txt  -> {"status":0, "...anexado com sucesso."} (FOUND)
  verify idUser=1721 nameFile=<uniq>.txt  -> {"status":-1, "...não foi salvo..."}     (NOT found)
  => An authenticated attacker can plant allowlisted-extension files into ANY other
     user's upload namespace (e.g. <victim_idUser>.<name>). The READ side is session-
     scoped (dowloadArquivoTemp prepends the session idUser), so the attacker cannot
     DOWNLOAD a victim's file this way; but the WRITE side is NOT scoped, enabling
     content-injection / namespace-pollution into other users' document workflows and
     potential INTEGRITY impact (e.g. pre-planting a file a victim's save flow may
     later associate/submit). Overwrite of an existing victim file was NOT tested
     (destructive) — flagged as a likely integrity risk to remediate.

### (D) RCE / webroot-landing — NOT achievable (REFUTED)
  * The upload base dir is NOT served as a static webroot via the public LB.
    Probes of every candidate served path returned genuine Tomcat 404s:
      /1721.<uniq>.txt, /<uniq>.txt, /test/..., /uploads/..., /arquivos/...,
      /fotoaluno/1721.<uniq>.txt, /resources/1721.<uniq>.txt, /imagemsite/...
    -> all HTTP 404 (Tomcat 404 page, ~770-800 B). Traversal writes (../, ../../,
       ../ROOT) likewise did not land in any served webroot path.
  * /fotoaluno/ (where student photos are served) is a CONTROLLER-mapped path
    (returns Tomcat 404 for arbitrary files), NOT a static webroot dir — and the
    photo endpoint /portal/RecebeImagem forces the .jpg extension server-side.
  * Combined with the .jsp/.war/.sh save-blocklist ((A) above), there is NO path to
    get an executable file persisted AND served+compiled by Tomcat. RCE REFUTED.

## Recommendation
1. Ignore the misleading "POST OK" ack; gate persistence on the extension allowlist
   (already done) — keep blocking .jsp/.jspx/.war/.sh/.html/.htm/.svg.
2. SANITIZE `diretorio`: reject any `..`, absolute paths, null bytes; force the value
   under a fixed base dir; derive the on-disk subpath server-side (do not trust the
   client `diretorio` for the storage location).
3. ENFORCE ownership on WRITE: ignore the client-supplied filename idUser prefix and
   always store as {session_idUser}.<server-uuid>; the read side is already session-
   scoped — make the write side session-scoped too. This kills the cross-user
   namespace-pollution / integrity vector.
4. Apply the same path/ownership hardening to /portal/RecebeImagem,
   /portal/verificaArquivoProfessor, /portal/dowloadArquivoTemp, /portal/deleteFile.
5. Confirm the upload base dir is outside the Tomcat webroot (it appears to be) and
   keep it that way; never serve it statically.
