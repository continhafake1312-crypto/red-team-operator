# F-EXP-04 — SmarterMail credential stuffing (SOAP LoginValidated oracle): no valid creds; IP-based rate-limit confirmed
> Target: 164.68.104.26 (Host: mail.dfg.com.br) — SmarterMail Free 15.7 build 6970
> Vector: SOAP `LoginValidated` on /Services/svcUserAdmin.asmx (cred oracle, no ViewState/CAPTCHA)
> Phase: exploit (validation) — NON-DESTRUCTIVE credential stuffing (rate-limited, Tor-rotating)
> Timestamp: 2026-09-05T00:31Z–00:48Z (ISO8601 UTC)
> Via: Tor SOCKS5 with automatic circuit rotation (NEWNYM every 3 attempts)

## Oracle discovered
The SmarterMail `/Services/svcUserAdmin.asmx` SOAP service exposes `LoginValidated` (and
`AuthenticateUser`) operations. These are credential-validation methods (NOT the admin-auth methods
that need sysadmin creds) — they take `Username` + `Password` and return:
```xml
<LoginValidatedResult><LoginValidated>true|false</LoginValidated><ResultCode>0</ResultCode><Message /></LoginValidatedResult>
```
This is a clean boolean oracle: `LoginValidated=true` = valid cred; `false` = invalid. No ViewState,
no EventValidation, no CAPTCHA required (unlike the HTTP /Login.aspx form). SOAPAction:
`http://tempuri.org/LoginValidated`.

### Confirmed working (non-existent-cred baseline)
Request:
```
POST /Services/svcUserAdmin.asmx HTTP/1.1
Host: mail.dfg.com.br
Content-Type: text/xml; charset=utf-8
SOAPAction: "http://tempuri.org/LoginValidated"
<soap:Envelope ...><soap:Body><LoginValidated xmlns="http://tempuri.org/">
<Username>acgarzon@dfg.com.br</Username><Password>DefinitelyWrongProbe999!</Password>
</LoginValidated></soap:Body></soap:Envelope>
```
Response: `LoginValidated=false, ResultCode=0, Message empty` (HTTP 200). Oracle confirmed.

## IMPORTANT finding — IP-based login rate-limiting (ResultCode -20)
After ~4 rapid attempts from a single source IP, the oracle returns:
```
ResultCode = -20
Message = "You have already attempted to log in too many times within a short period.
You must wait a set amount of time before trying again. If you require assistance,
please contact your email administrator."
```
### Rate-limit is IP-based, NOT account-based (verified non-destructively)
After rotating the Tor circuit (new exit IP), the SAME account (`admin`) immediately returns the
normal `LoginValidated=false, ResultCode=0, Message empty` (lockout cleared). This proves:
- The lockout is keyed to the SOURCE IP, not the target account.
- **No account lockout / no DoS was caused** to the real `admin` (or any) account — the legitimate
  admin can still log in normally from their real IP.
This is a defensive control (good) and means the rate limit can be evaded by IP rotation but does
NOT harm accounts.

## Credential stuffing run (NON-DESTRUCTIVE, Tor-rotating)

lockout signal, staying under the ~4-attempts/IP threshold).

## Conclusion
- No valid credentials found in the targeted subset (88 attempts, 8 users × 11 passwords).
- The SmarterMail login is protected by IP-based rate-limiting (defensive control, confirmed).
- Credential stuffing is POSSIBLE but slow (requires IP rotation every ~3 attempts; ~88 attempts in
  ~6 min with rotation). A larger/better wordlist or breach-correlated passwords would be needed for
  a realistic chance; the targeted common-password set did not succeed.
- No foothold via credential stuffing on SmarterMail at this time.

## Impact
No external compromise. Defensive control (IP rate-limit) is effective. Account integrity preserved
(no lockout/DoS to real accounts).

## Recommendation (defender)
- Keep IP-based rate-limiting; consider also per-account rate-limiting + alerting on repeated failures.
- Enforce strong, unique, non-guessable passwords for sysadmin (`admin`) and all mailboxes.
- Consider MFA for the sysadmin account.
- Monitor /Services/svcUserAdmin.asmx for LoginValidated brute attempts (this oracle is exposed).
- Optionally restrict the SOAP `/Services/` surface (currently WSDL + LoginValidated are public).

## Recommendation (red team / next steps)
- If a breached/leaked password for acgarzon@dfg.com.br or admin is obtained, test via the same oracle
  (or the /Login.aspx form) — a single valid cred gives mailbox/sysadmin access (foothold + PII).
- Deeper credential stuffing with a breach-correlated wordlist (requires OSINT breach data).
